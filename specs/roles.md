## 1. 나눈 기준

1. **기능적으로 이어지는 것끼리** 묶는다 — 같은 데이터·같은 화면 흐름을 한 사람이 맡아야 인터페이스가 줄어든다.
2. **양(화면·API 수)과 난이도(로직)를 함께** 맞춘다 — 폼이 많은 묶음과 로직이 어려운 묶음이 비슷한 무게가 되게.
3. 채팅은 **한 사람이 전담**한다 (D-20).
4. 팀장은 리뷰·머지·스펙 관리를 함께 하므로, 팀장 묶음은 연결이 많은 대신 양을 줄인다.

### 부하 점검 (v0.3)

오퍼·관심 업체(4개)와 새 결정(게시판 3개, 프로필 3개)이 1번에 들어가 **1번 38개 vs 2번 19개**로 차이가 커졌다. 1번 기준 대부분이 단순한 폼·조회라 수만큼 무겁지는 않지만, 일정이 밀리면 아래 순서로 넘긴다.

1. **공간 등록·탐색(SPACE, 4개) → 2번** — 공간 스냅샷을 쓰는 곳이 2번이라 기능 연결도 자연스럽다 (1번 34 / 2번 23).
2. 그래도 밀리면 **개인 프로필(PROFILE-02, 2개) → 3번** — 업체가 공고·채팅에서 사용자를 볼 때 쓰는 화면이다.

## 3. 묶음 사이의 약속 (인터페이스)

먼저 정해 두면 서로 기다리지 않고 동시에 개발할 수 있다. 정한 함수 이름·형식은 각 모듈의 `service.py`에 먼저 빈 함수로 만들어 둔다.

| 주는 쪽 → 받는 쪽 | 약속 | 언제 필요 |
|---|---|---|
| 1 → 전원 | **개발용 가짜 로그인** (`APP_ENV=test`에서 역할만 골라 로그인) — 1번 완성 전에도 각자 화면 테스트 | **첫날** |
| 1 → 전원 | `current_user` 의존성, `require_role()`, 업체 승인·정지 확인 `can_send_quotes()` (이미 있음) | 첫 주 |
| 1 → 2 | 공간 조회·스냅샷 `get_venue_snapshot(venue_id)` | 요청서·배정 |
| 2 → 1·3 | 열린 단계 조회 `get_open_stage(performance_id)` — 오퍼 대상 단계, 공고 노출 조건 | 오퍼, 공고 목록·견적 |
| 3 → 2 | 컨펌 시 `stage_confirmed(stage_id, quote_version_id)` 호출 → 2가 [다음 단계로] 준비 | 채팅 확정 |
| 4 → 3 | `run_checks(...) -> list[CheckResult]` — `CONFLICT`면 컨펌 막기 | 채팅 확정 |
| 2·3 → 4 | 확정 견적서 버전 목록 `confirmed_lines(performance_id)` | 청구서 |
| 4 → 1·3 | 신고 `report(...)`, 경고 `warn(...)` (이미 있음), 블라인드 `blind_post(...)` | 채팅·게시판 신고 |
