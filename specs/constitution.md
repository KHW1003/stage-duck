# STAGE DUCK 프로젝트 원칙 (Constitution)

| 항목 | 내용 |
|---|---|
| 버전 | 0.1 (초안) |
| 작성일 | 2026-11-12 |
| 상태 | 팀 합의 전 초안 |
| 적용 범위 | 이 저장소의 모든 스펙·계획·코드·문서 |

> 이 문서는 STAGE DUCK을 만들면서 **어떤 결정도 어기면 안 되는 기준**이다.
> 스펙(spec.md), 계획(plan.md), 코드가 이 원칙과 충돌하면 원칙을 따르거나, 원칙을 먼저 개정한다.

---

## 1. 스펙이 먼저다 (Spec First)

- 기능은 **spec.md에 수용 기준이 생긴 다음에** 계획하고 구현한다.
- 스펙에 없는 기능을 코드에 먼저 넣지 않는다. 필요하면 스펙 PR을 먼저 올린다.
- 스펙은 **무엇을·왜**만 쓴다. 기술 선택(어떻게)은 plan.md에 쓴다.
- 모든 계획·코드·테스트는 스펙의 ID(`F1`, `AC-F1-01`, `FR-AUTH-01`)로 추적할 수 있어야 한다.

## 2. 공연을 준비하는 사람의 문제에서 출발한다

- 대상은 **500명 이하 소규모 공연**의 주최자다 (인디 밴드, 소극단, 교회, 학원 등).
- 장비를 모르는 사람도 쓸 수 있어야 한다. 전문 품목을 몰라도 공연 형태와 필요한 것만으로 요청할 수 있게 한다.
- 기능을 추가할 때 "이게 사용자의 공연 준비를 더 쉽고 확실하게 만드는가?"를 먼저 묻는다.

## 3. 공연장 → 장비 → 엔지니어 순서를 지킨다

- 배정은 항상 **공연장 → 장비 → 엔지니어** 순서다. 앞 단계가 정해져야 다음 단계 업체가 공고를 본다.
- 이미 가진 것, 공연장이 갖춘 것은 건너뛸 수 있지만, 건너뛰기는 **사용자가 직접 선택**하고 책임 고지에 동의한다.
- 직접 오퍼·게시판 같은 다른 기능도 이 순서를 깨지 않는다.

## 4. 합의는 플랫폼 안에서, 기록은 지우지 않는다

- 견적 조율·컨펌·결제는 **플랫폼 안에서** 한다. 이것이 노쇼 방지와 신뢰의 근거다.
- 요청서·견적서는 고칠 때마다 **새 버전**을 만들고 이전 버전을 지우지 않는다.
- 컨펌·결제 시점의 조건은 **스냅샷**으로 보관한다. 원본이 바뀌어도 합의된 조건은 바뀌지 않는다.
- 이전 버전에 대한 합의(컨펌)를 새 버전에 재사용하지 않는다.

## 5. 시스템은 판정하지 않고 보여준다

- 사이트는 인원·시간·중복 같은 **입력된 값끼리의 충돌**만 자동으로 검사한다.
- 소리 크기, 장비 호환성, 현장 안전은 **자동으로 판정하지 않는다.** 현장을 맡은 엔지니어·업체가 확인하고 기록한다.
- 업체가 수락하기 전에는 어떤 화면도 "공연 가능 확정"이라고 안내하지 않는다.

## 6. 서버가 기준이다

- 권한, 금액, 상태 변경은 **서버에서 검사한다.** 화면에서 버튼을 숨기는 것은 보조 수단이다.
- 금액·합계·결제·위약금은 서버가 계산한다. 화면에서 보낸 금액은 믿지 않는다.
- 같은 요청이 두 번 와도 한 번만 반영한다 (결제, 컨펌).
- 상태는 정해진 순서를 벗어날 수 없다.

## 7. 개인정보는 최소로 받고, 연락처는 지킨다

- 쓰임이 없는 정보는 받지 않는다 (예: 사용자 주소는 받지 않는다).
- 사용자·업체 연락처는 **결제 전에는 공개하지 않는다.** 결제 후 최종 담당표에서만 공개한다.
- 업체 사업자 정보는 관리자만 본다.
- 비밀 값(키, 비밀번호)은 저장소에 넣지 않는다.

## 8. 시뮬레이션임을 정직하게 밝힌다

- 공간·업체·엔지니어·가격은 모두 **가상 데이터**다. 실제 회사 이름이나 실제 개인정보를 쓰지 않는다.
- 결제·위약금·환불은 **모의(테스트)** 로만 동작하고, 화면에 항상 그렇게 표시한다.
- 시연 결과를 실제 시장 검증이나 실제 거래 성과로 소개하지 않는다.

## 9. MVP 범위를 지킨다

- 범위 밖(후속) 기능은 spec.md의 "범위 밖" 목록에 적고, 일정 안에서 MVP를 먼저 끝낸다.
- 현재 후속: 리얼 후기, 익스프레스, 이모티콘, 실결제·실정산, 전자계약, 메일·문자 알림, AI 추천 등.
- 범위를 바꾸려면 팀 합의 후 스펙과 이 목록을 먼저 고친다.

## 10. 수용 기준은 테스트할 수 있어야 한다

- 모든 수용 기준은 **Given-When-Then** 형식으로 쓴다.
- 수용 기준마다 대응하는 테스트를 두고, 테스트 이름에 수용 기준 ID를 적는다.
- 팀원 PR은 CI 테스트를 통과해야 머지된다.

## 11. 각자 끝까지 책임지고, 공통 약속은 함께 정한다

- 각 담당자는 맡은 기능을 **화면 → API → DB → 권한 → 테스트까지** 끝까지 책임진다.
- 다른 담당자에게 영향을 주는 것(역할·권한, DB 스키마, API·오류 형식, 날짜·금액 규칙, 공통 화면)은 혼자 바꾸지 않고 합의한다.
- 모든 변경은 PR로 올리고, 다른 사람 1명 이상이 리뷰한다.

---

## 개정 절차

1. 개정이 필요하면 이슈를 만들고 이유를 적는다.
2. 팀 회의(또는 이슈 댓글)에서 합의한다.
3. 이 문서를 PR로 고치고 버전과 개정 이력을 올린다.
4. 원칙이 바뀌면 영향을 받는 spec.md·plan.md도 같은 PR이나 바로 다음 PR에서 맞춘다.
