## 1. 사업과 프로젝트 개요

### 우리가 하는 사업
공연 주최자와 공연장·복합문화공간·음향업체·엔지니어를 연결하는 공연 준비 중개 플랫폼이다. 공간, 장비, 인력을 각각 찾던 일을 공연 한 건 안에서 처리한다.

전문 공연장은 기본 제공 장비와 인력을 먼저 반영하고, 부족한 부분만 추가한다. 옥상·정원·창고 등 이색 공간은 공연 허용 조건을 공간 운영자가 확인한 뒤, 그 조건을 본 음향업체가 장비·설치·운영 인력을 제안한다.

장비를 잘 모르는 소비자가 제품을 하나씩 골라 기술적 호환성을 책임지는 방식보다는, 전문가가 제안하고 공간 측이 필요한 조건을 확인한 구성을 소비자가 비교하는 방식을 우선한다. 공연 가능성이나 현장 안전을 프로그램이 자동으로 보증하지 않는다.

### 목표 사용자
- **공연 주최자**: 전국에서 예상 관객 500명 이하의 공연을 준비하는 밴드·동아리·소규모 기획자.
- **공간 운영자**: 전문 공연장뿐 아니라 공연을 허용하는 복합문화공간·정원·옥상·창고 공간 운영자.
- **음향업체**: 장비 대여, 운반, 설치·철수, 현장 운영을 제공하는 업체.
- **엔지니어**: 공간·장비·근무 조건을 확인하고 공연 운영을 맡는 음향기사.

대표 시연은 광주의 80명 밴드 공연으로 하되, 서비스의 지역 선택은 전국을 지원한다.

### 해결하려는 문제와 차별화 가설
- 공간을 발견해도 실제 밴드 공연이 가능한지, 어떤 장비와 인력이 포함되는지 불명확하다.
- 공간·장비·기사에게 같은 조건을 각각 설명하고, 서로 다른 견적의 포함 항목을 맞춰봐야 한다.
- 저렴한 견적을 골라도 설치와 리허설 시간이 맞지 않거나 필요한 장비가 빠질 수 있다.
- 가격이나 시간이 바뀐 뒤 누가 어떤 조건에 동의했는지 추적하기 어렵다.

차별화의 중심은 공간 조건을 기준으로 견적을 받고, 총비용·포함 범위·준비 일정을 같은 기준으로 비교하며, 업체별 합의를 남기는 것이다. 경쟁 서비스에 동일 기능이 전혀 없다고 주장하지 않는다. 실제 수요와 수수료 수용성은 별도 현장 검증 대상이다.

## 2. 서비스 구성

| 기능 | 주최자에게 제공하는 가치 |
|---|---|
| 공간 탐색 | 지역·일정·인원·공연 형태에 맞는 공간과 기본 장비·인력·이용 조건 확인 |
| 공연 요청서 | 공연 개요, 리허설, 장비 요구사항, 이미 확보한 자원을 한 번 입력 |
| 전문가 견적 | 공간을 본 업체가 부족한 장비와 설치·운영 인력을 포함해 제안 |
| 패키지·조합 비교 | 공간 측의 전체 패키지와 공간+외부 음향 제안을 총액과 조건으로 비교 |
| 업체별 확인 | 선택한 조합을 각 담당자가 수락·거절하고, 기술 확인이 필요한 항목을 처리 |
| 결제·최종 일정 | 테스트 결제 후 업체별 담당 범위와 최종 일정을 한 화면에서 확인 |

기본 진행 순서: 공간 후보 선택 → 공간 조건 확인 → 음향 견적 요청 → 제안 비교 → 업체별 최종 확인 → 테스트 결제 → 섭외 확정.

공간 후보 선택은 예약 확정이 아니다. 업체는 입실 가능 시간과 견적 유효기한을 제안하고, 최종 확인 단계에서 해당 일정을 다시 확인한다. 이미 외부에서 공간을 예약한 주최자는 공간 정보를 등록하고 추가 장비·인력만 요청할 수 있다.

## 3. 사용자와 권한

| 역할 | 허용되는 작업 |
|---|---|
| 주최자 | 자기 공연과 요청서 작성·수정, 공간 선택, 요청 공고 게시·마감, 받은 견적 비교, 조합 선택, 확인 요청, 테스트 결제 |
| 공간 운영자 | 자기 공간과 기본 제공 장비·인력 등록, 공연 허용 조건 답변, 공간·전체 패키지 견적 제출, 반입·설치 조건 확인 |
| 음향업체·기사 | 게시된 요청 공고 확인, 자기 제안 작성·수정·철회, 기술 조건 확인, 선정된 제안의 최종 수락·거절 |
| 플랫폼 관리자 | 공급자 가입 심사·승인·반려·정지, 게시 정보·신고·거래 이력 확인 |

공급자는 심사 승인 후 게시된 요청 공고를 보고 견적을 제출한다. 미승인 공급자는 공고 목록을 볼 수 없다. 다른 업체의 견적은 보지 못하고, 주최자는 자기 공연에 제출된 견적을 비교한다. 한 공급자가 공간·장비·인력을 여러 부문에서 제공할 수 있으므로, 계정과 제공 서비스 종류를 분리한다. 관리자는 당사자의 수락이나 결제를 대신 확정하지 않는다.

## 4. 상세 이용 시나리오

### A. 전문 공연장 이용
주최자가 기본 음향과 기사가 포함된 공간을 고른다. 요청한 장비·운영 시간이 기본 제공 범위에 들어가면 공간 패키지만 선택한다. 부족한 무선마이크나 녹음 서비스가 있다면 추가 요청한다. 모든 공연에 외부 장비·기사를 의무적으로 붙이지 않는다.

### B. 이색 공간에서 밴드 공연 — 대표 MVP 시나리오
1. 주최자가 "토요일 19~21시, 80명, 리허설 17시, 보컬 마이크 4개"를 등록한다.
2. 복합문화공간 후보의 입실·퇴실, 기본 장비, 공연 허용 여부와 외부 음향 반입 조건을 확인한다. 미확인 조건은 표시하고, 확인 전에는 최종 확정 요청을 막는다.
3. 음향업체가 공간 정보를 보고 "추가 마이크 2개, 밴드용 음향 구성, 설치·철수, 현장기사 포함" 제안을 보낸다. 전문 품목을 모르는 주최자는 공연 형태와 편성으로 요청하고 업체가 구성을 제안할 수 있다.
4. 주최자는 전체 패키지와 공간+음향업체 제안을 비교한다. 시스템은 입력된 수량과 시간 충돌을 표시하고, 공간 운영자와 업체는 반입·전원·연결 조건 등 기술 확인을 기록한다.
5. 선택된 조합의 공급자가 자기 담당 범위와 최종 일정을 수락하면 테스트 결제로 넘어간다.
6. 결제 성공을 서버에서 확인한 뒤 섭외 확정 상태와 최종 담당표를 보여준다.

### C. 버스킹 장비 대여 — 후속 확장
공간을 이미 확보한 이용자가 휴대용 음향 장비만 요청하거나 설치·기사까지 선택한다. 장소 사용 조건은 별도 확인한다. MVP에서는 요청 유형의 확장 방향으로 정리하고, 별도 배송·보증금·파손 정산 흐름은 구현하지 않는다.

## 5. 가상 회사·공간 기반 MVP 시뮬레이션

### 시뮬레이션 원칙
- 공간명·업체명·엔지니어·장비·가격·일정·기술 조건을 모두 가상 데이터로 구성한다. 실제 회사나 공간과의 제휴·예약·현장 검증을 전제로 하지 않는다.
- 주최자·공간 운영자·음향업체·기사·관리자 계정을 준비해 팀원이 역할을 바꿔가며 요청·견적 제출·확인·수락을 직접 시연한다.
- 초기 가상 데이터를 미리 넣되, 화면에 고정된 결과만 보여주지 않는다. 견적 수정·시간 변경·수락·거절은 실제 서버와 DB로 처리하고 새로고침 후에도 유지한다.
- 공간 측과 음향업체의 기술 확인도 가상 담당자 계정으로 기록하는 절차를 검증한다. 실제 장소에서 공연이 가능하다고 검증한 결과로 소개하지 않는다.
- 결제는 테스트 모드 또는 모의 결제로 진행하며 실제 청구·대관·파견·정산은 발생하지 않는다. 결제 화면에 테스트 결제임을 표시한다.
- 데이터는 재현 가능한 초기 상태로 준비한다. 시연용 데이터 초기화는 관리자 권한의 테스트 환경에서만 수행하며 일반 사용자 기능과 분리한다.

### 가상 공급자 7곳과 대표 비교 화면
가상 업체명·가격·거래임을 명확히 표시한다. 실제 업체 참여나 실제 거래 성과로 소개하지 않는다.

| 가상 공급자 | 제안 역할 |
|---|---|
| A 라이브홀 | 공간·장비·기사 전체 패키지 400만 원 |
| B 루프탑 | 공간 40만 원, 17시 입실 가능 |
| C 컬처스페이스 | 공간 50만 원, 15시 입실 가능 |
| D 사운드 | 음향 구성·설치·철수·현장기사 포함 125만 원, 사전 기술 협의 가능 |
| E 오디오 | 비교용 음향 구성 제안, 요청 조건 중 미확인 항목을 남겨 확인 절차 시연 |
| F 엔지니어 | 현장 운영 단독 제안. 장비만 제공하는 제안과 조합할 때 선택 가능 |
| G 엔지니어 | 비용과 근무 가능 시간이 다른 단독 제안 |

B와 C 공간은 대표 시연에서 유선 보컬마이크 2개를 제공하되, 실제 사용 가능 여부와 나머지 음향 구성은 업체와 확인하는 것으로 설정한다. D 견적의 기사는 이미 포함되므로 F·G를 중복으로 추가하지 않는다. D의 설치에는 90분이 필요하다고 입력한다.

| 비교 대상 | 총액 | 표시할 이유 |
|---|---|---|
| A 전체 패키지 | 400만 원 | 공간·음향·기사 포함, 입력 조건과 기술 확인 완료 |
| B 40만 + D 125만 | 165만 원 | 17시 입실 후 설치 90분 필요 → 17시 리허설과 충돌 |
| C 50만 + D 125만 | 175만 원 | 15시 입실 → 16시 30분 설치 완료, 기술 확인 완료 후 선택 가능 |

대표 화면은 견적 비교 화면으로 한다. 공연 조건, 기본 제공 항목, 추가 제공 항목, 포함·별도 비용, 총액, 일정 충돌, 기술 확인 상태를 함께 보여준다. 조건 확인은 가격과 별개로 표시하고, 업체 확인 전에는 '공연 가능 확정'으로 안내하지 않는다.

## 6. 검증과 상태 변경 규칙

### 시스템이 검사할 것
- 예상 관객은 1~500명 범위로 입력하고, 선택 공간의 허용 인원과 비교한다.
- 기본 제공과 추가 제공 장비를 합산해 명시된 필수 수량과 비교한다. 마이크 같은 단순 품목부터 검사한다.
- 공간 입실 ≤ 설치 시작, 설치 완료 ≤ 리허설 시작을 검사한다.
- 엔지니어 근무가 합의된 리허설·공연 운영 시간을 포함하고, 철수가 퇴실 마감 안에 끝나는지 검사한다.
- 고객에게 청구되는 최종 합계와 별도 비용을 표시한다. 총액에 포함되는 세금·운반·설치비는 견적 입력 규칙을 통일한다.
- 이미 포함된 기사나 동일 항목을 중복 선택했을 때 알린다.
- 필수 정보가 없으면 '확인 필요', 입력 조건이 어긋나면 '충돌'로 표시한다. 예산 초과는 별도 경고다.

### 당사자가 확인할 것
공간의 공연 허용 조건, 외부 장비·기사 허용, 전원과 반입 동선, 연결·설치 가능 여부, 야외 운영 조건 등은 공간 측과 음향업체가 확인한다. 담당자, 확인일, 대상 요청서·견적 버전과 답변을 남긴다. 소리 크기나 장비 호환성을 사이트가 자동으로 판정하지 않는다.

### 수정 견적과 재합의
확정 요청 시점의 금액·품목·일정을 보관한다. 조건 변경 시 업체가 수정 견적 제출 → 주최자가 새 조합 선택 → 기술·일정 재확인 → 선택 업체 전원 수락 → 결제 가능 순서로 진행한다.

예를 들어 C+D 175만 원 조합의 리허설을 17시에서 16시로 바꾸면 기존 설치 완료 16시 30분과 충돌한다. D가 "설치 인력을 추가해 15시 45분 완료, 10만 원 추가"를 제안하면 새 조합은 185만 원이다. 주최자와 선정 업체들이 새 조건에 동의하기 전에는 확정하지 않는다. 이전 175만 원 이력은 유지한다.

이미 결제한 거래의 조건은 새 견적이 나와도 자동으로 바뀌지 않는다. 결제 후 변경·추가 결제·환불 절차는 후속 범위로 둔다.

### 상태와 결제
- 공연 진행: 작성 중 → 공간 후보 선택 → 견적 모집 → 조합 선택 → 업체 확인 중 → 결제 대기 → 섭외 확정.
- 업체별 확인: 대기 / 수락 / 거절 / 만료. 새 조합에는 새 확인 기록을 사용한다.
- 필수 확인 누락, 충돌, 업체 거절·만료가 있으면 결제 불가. 거절 시 재선택한다.
- 결제 실패는 확정으로 처리하지 않는다. 동일 결제 응답은 한 번만 반영하고 한 공연에서 두 조합이 중복 확정되지 않게 한다.
- 최종 확인에는 기한을 두고, 만료 후에는 일정 재확인을 받는다. 외부 업체의 전국 재고·달력을 실시간 보증하는 기능은 MVP에 넣지 않는다.
- 테스트 결제와 정산 예정액만 보여주며 실제 돈이나 업체 정산은 발생하지 않는다.

## 7. 4인 풀스택 역할 분담

각 팀원은 자기 기능의 화면·요청 검증·처리 로직·DB 저장·권한 확인·검증을 끝까지 담당한다. 프론트·백엔드·DB를 사람별로 나누지 않는다.

| 담당 | 담당 기능·화면 | 서버·데이터 책임 | 완료 기준 |
|---|---|---|---|
| 1. 공연 요청·공간 선택 | 주최자 공연 등록·수정, 전국 공간 목록·상세·선택, 요청 공고 게시·마감·현황 | 공연 요청, 필수 항목, 선택 공간, 요청 버전, 공고 상태. 요청 소유권 확인 | 신규 공간 선택과 이미 확보한 공간 입력을 지원하고, 선택 공간 조건이 업체 요청 화면에 전달된다. |
| 2. 공급자 등록·전문가 견적 | 공급자 입점 신청, 관리자 심사, 공간·서비스 등록, 업체 요청 목록·견적 작성 | 공급자 프로필·승인 상태, 공간 기본 제공 정보, 견적·항목·버전. 업체는 자기 정보만 수정 | 가상 공급자 승인 후 공간·장비·기사의 단독·통합 제안을 등록하고 경쟁 업체 견적은 볼 수 없다. |
| 3. 견적 비교·구성 확인 | 전체 패키지와 공간+음향 제안 비교, 조합 선택, 수량·시간 경고, 기술 확인 답변 화면 | 조합·구성 항목·판정 결과·기술 확인 기록. 요청·견적 변경 시 다시 검사 | 165만 원 조합의 충돌과 175만 원 조합의 확인 상태를 구분하고, 기사 중복과 수량 부족을 표시한다. |
| 4. 업체 수락·결제·확정 | 업체별 수락·거절, 주최자 확인 현황, 테스트 결제, 최종 일정·담당표, 거래 이력 | 확인 요청과 응답, 주문·결제 시도·거래 이력. 결제 가능 조건과 중복 처리 검증 | 미확인 조합은 결제할 수 없고, 모두 수락한 유효 조합만 테스트 결제로 확정된다. |

**공통 작업**: 계정·역할 정의, 로그인, 공통 화면 틀, 오류 형식, 날짜·금액 규칙, 기능별 입력·응답 문서를 초기에 함께 만든다. 상세 구현 담당과 검토자는 착수 때 지정한다. 관리자 화면은 2번의 입점 심사와 4번의 거래 이력을 같은 메뉴에서 연결한다.

**공간 데이터 소유권**: 2번은 공간 운영자의 원본 정보를 등록·수정한다. 1번은 이를 조회·선택하고 공연 요청에 적용된 조건을 보관한다. 원본 공간 정보가 바뀌어도 과거에 합의한 조건은 덮어쓰지 않는다.

## 8. 주요 화면과 데이터 연결

- **주최자**: 시작·공간 탐색 → 공연 요청서 → 받은 제안 → 견적 비교 → 업체 확인 현황 → 결제 → 최종 일정.
- **공급자**: 가입·심사 상태 → 공간·서비스 관리 → 요청 공고 목록 → 견적 제출 → 기술 확인 → 최종 수락 → 확정 내역.
- **관리자**: 공급자 심사 → 공간·게시 정보 확인 → 신고·거래 이력.

| 데이터 묶음 | 담당과 연결 |
|---|---|
| 계정·역할 | 공통. 주최자·공간 운영자·업체·기사의 권한 구분 |
| 공급자·공간·제공 서비스 | 2번 등록 → 1번 탐색·선택 |
| 공연 요청·공고 | 1번 작성·게시 → 2번 공고 목록·견적 작성에 사용 |
| 견적·포함 항목·버전 | 2번 작성 → 3번 비교·검증 |
| 조합·기술 확인 | 3번 관리 → 4번 최종 확인·결제 조건에 사용 |
| 업체 수락·주문·결제·거래 이력 | 4번 관리 → 주최자·업체의 확정 화면에 표시 |

테이블 수와 최종 구조는 개발 설계에서 확정한다. 공간 후보, 기술 확인, 업체 수락, 결제 완료는 서로 다른 상태로 관리한다.

## 9. 개발 범위와 검증

### 필수 MVP
- 전국·500명 이하 공연 요청과 가상 공간 탐색. 전국은 지역 선택 범위이며, 실제 전국 업체 확보나 모든 지역의 공간 등록 완료를 뜻하지 않는다.
- 가상 공급자 7곳의 등록·승인·견적 작성.
- 전문 공연장 패키지와 이색 공간+외부 음향 제안 비교.
- 기본 제공 장비 반영, 부족 수량·일정 충돌 표시, 기술 확인 기록.
- 업체별 수락·거절, 수정 견적 재확인, 테스트 결제와 최종 일정표.
- 역할·소유권별 접근 제한과 상태 변경 이력.

### 개발 순서
1. **공통 약속**: 역할·공연 ID·요청/견적 버전·기술 확인과 수락 상태·화면 간 전달 항목을 합의한다.
2. **첫 통합**: 공간 하나 선택 → 요청 작성 → 음향 제안 한 건 → 기술 확인 → 두 공급자 수락 → 테스트 결제.
3. **차별점 완성**: 패키지와 두 공간 조합을 비교하고 저렴하지만 리허설을 놓치는 경우를 보여준다.
4. **예외 검증**: 미승인 업체 제출, 다른 업체 견적 열람, 관객 501명, 기사 중복, 수락 누락, 변경 전 수락 재사용, 결제 실패·중복 응답을 검사한다.
5. **발표**: 주최자·업체·관리자 계정을 번갈아 사용해 요청부터 확정까지 실제 저장과 상태 변화를 시연한다.

### 보류 기능
전국 실제 업체 입점 확대, 특정 업체 지정 초대, 버스킹 장비의 별도 대여·회수, 재고 실시간 예약, 실결제·환불·업체별 정산, 전자계약, 채팅, 커뮤니티·후기, AI 자동 구성은 후속으로 둔다. 기술 스택은 추후 결정한다.

## 10. 수익 구조와 사업 검증

주 수익 가설은 성사 거래에 대한 업체 중개 수수료다. 조합별 총액과 공급자별 거래금액을 기준으로 계산하고, 전체 패키지에는 한 번만 적용한다. 정확한 요율과 결제 비용 부담은 아직 미정이다.

첫 2~3건의 플랫폼 중개 수수료 면제를 검토한다. 결제 비용까지 무료라는 의미는 아니며 실제 운영 전에 조건을 정한다. 추후 반복 이용 공급자에게 견적·일정·고객 관리 구독을 제공하는 방향도 검토한다.

포트폴리오 MVP는 가상 회사·공간·엔지니어를 이용해 기술 동작과 역할별 업무 흐름을 입증하는 단계다. 실제 시장 수요나 업체 참여를 검증한 단계로 소개하지 않는다. 실제 사업성은 유료 거래에서 비교 가능한 제안 수, 예약 전환, 주최자의 재이용, 업체의 수수료 수용성, 거래 한 건당 운영 개입 시간으로 검증한다. 자동화보다 운영자가 직접 조율하는 시간이 커지면 대행 서비스에 가까워지므로 수익성과 인력 부담을 함께 확인한다.
