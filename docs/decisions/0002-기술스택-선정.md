# 0002. 기술 스택 선정

- 날짜: 2026-11-12
- 상태: 확정 (팀장 결정) — 세부 라이브러리는 (제안)

## 배경
Day 3(Plan)에서 spec.md를 구현할 기술을 정해야 한다. 핵심 요구는 순차 배정 상태 흐름, 실시간 채팅(D-7b), 동시 컨펌·중복 결제 방지, 에스크로형 모의 결제 장부다.

## 결정

| 영역 | 확정 | 세부 (제안) |
|---|---|---|
| 프론트엔드 | **React + Vite** | TypeScript, React Router, TanStack Query |
| 백엔드 | **FastAPI** (Python) | Python 3.12, Pydantic v2, Uvicorn |
| DB | **MariaDB** | 11.4 LTS, InnoDB, utf8mb4 |
| ORM | **SQLAlchemy** | 2.0 (동기 세션) + PyMySQL 드라이버, Alembic 마이그레이션 |
| 백엔드 테스트 | **pytest** | httpx(TestClient), pytest-cov, 테스트용 MariaDB 컨테이너 |
| 프론트 테스트 | **React 표준 도구** | Vitest + React Testing Library + MSW (API 목업). 대표 시나리오 E2E는 Playwright (권장) |
| 실시간 채팅 | FastAPI WebSocket | 서버 1대 기준 메모리 연결 관리 |
| 관리자 화면 | **SQLAdmin** | 모델 기반 자동 생성 + 커스텀 액션. Figma·React 화면 없음 |
| 배포·실행 | Docker Compose | backend, frontend, mariadb 3개 서비스 |

## 선택 이유
- **프론트 테스트 — Vitest + React Testing Library**: React 컴포넌트 테스트에서 가장 널리 쓰이는 조합은 Jest + React Testing Library다. Vite 프로젝트에서는 Jest 대신 Vitest를 쓰면 별도 변환 설정 없이 Vite 설정을 그대로 쓰고, Jest와 거의 같은 문법(`describe`, `it`, `expect`)을 쓴다. React Testing Library는 둘 다 같다.
- **TypeScript**: API 응답 형식을 타입으로 맞춰 두면 4명이 영역을 나눠 개발할 때 계약 위반을 컴파일 단계에서 잡는다. 팀이 JavaScript를 원하면 바꿀 수 있다.
- **SQLAlchemy 동기 세션**: 비동기보다 코드와 테스트가 단순하다. FastAPI는 동기 엔드포인트를 스레드 풀에서 실행하므로 MVP 규모에서 충분하다.
- **MariaDB 주의점**: 조건부 유니크 인덱스(부분 인덱스)가 없어서 "공연당 열린 단계 1개", "공연당 유효 주문 1개" 같은 제약은 **생성 컬럼 + 유니크 인덱스**와 **행 잠금(`SELECT … FOR UPDATE`)** 으로 만든다 ([data-model.md](../../specs/data-model.md) 참고).

- **SQLAdmin**: 관리자 화면은 내부 도구라 디자인이 필요 없다. SQLAlchemy 모델에서 목록·상세를 자동으로 만들고, 승인·경고 같은 업무는 액션 버튼으로 서비스 함수를 부른다. 화면 개발 시간을 사용자 기능에 쓴다.

## 영향
- CI의 `test` 작업을 `pytest` + `vitest run`으로 교체한다 (job 이름 `test` 유지 — 룰셋 필수 검사).
- 저장소 구조: `backend/`, `frontend/`, `docker-compose.yml`.
- `.gitignore`에 Python 항목은 이미 있다.
