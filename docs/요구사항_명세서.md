## 1. 문서 개요

### 1.1 목적
이 문서는 공연 공간·음향 섭외 플랫폼 **STAGE DUCK**의 **MVP 범위를 개발·테스트할 수 있는 수준으로** 정의한다.
각 기능은 ID, 설명, 처리 규칙, 예외, 수용 기준을 가진다. 설계·개발·테스트는 이 문서의 ID를 기준으로 추적한다.

### 1.2 범위
| 구분 | 이 문서에서 다루는 수준 |
|---|---|
| MVP | **상세** (기능별 규칙과 수용 기준) |
| 후속 기능 | 목록만 (9장) |

MVP는 **포트폴리오용 시뮬레이션**이다. 공간·업체·엔지니어·가격은 모두 가상 데이터이고, 결제·위약금·환불은 테스트(모의)로만 동작한다.

### 1.3 표기 규칙
- **우선순위**: `필수` = MVP 완료 조건 / `권장` = 일정이 허락하면 MVP에 포함 / `선택` = 후속
- **(제안)**: 팀이 정하지 않아 작성자가 채운 값·정책. 검토 후 확정하면 표시를 지운다.
- **[결정 D-n]**: 10.2 결정 체크리스트의 n번에서 고른다.
- **[자문]**: 현장 전문가(목산님) 확인이 필요한 항목.
- 기능 ID: `FR-<영역>-<번호>`, 비기능 ID: `NFR-<영역>-<번호>`

### 1.4 영역 코드와 담당

| 코드 | 영역 | 담당 (총계획서 7장 기준, 재조정 가능) |
|---|---|---|
| AUTH | 회원가입·로그인·역할 | 공통 |
| SUP | 업체 입점·심사 | 2 |

| QUOTE | 견적 작성·수정 | 2 |
| CHAT | 채팅·견적서 전송·확정 | 3 + 4 |

| TECH | 기술 확인 기록 | 3 |

### 1.5 용어 정의

| 용어 | 정의 |
|---|---|
| 사용자 (유저) | 공연을 준비하며 공간·장비·인력을 찾는 사람 (밴드, 극단, 교회, 학원 등) |
| 업체 (공급자) | 공간·장비·인력을 제공하는 회원. 공연장 업체, 장비 업체, 엔지니어를 통칭 |
| 제공 서비스 | 업체가 제공하는 부문. `공간` / `음향 장비` / `설치·철수` / `현장 운영(엔지니어)`. 한 업체가 여러 부문을 가질 수 있다 |
| 공연 요청서 | 사용자가 작성하는 공연 조건 문서. STEP1 공연 기본 정보 + STEP2 필요한 것 |
| 공고 | 게시된 공연 요청서. **현재 배정 단계**에 해당하는 업체가 보고 견적을 보낸다 |
| 배정 단계 | 공연장 → 장비 → 엔지니어 순서로 하나씩 업체를 정하는 단계 |
| 러브콜 | 업체가 공고를 보고 사용자에게 견적서를 보내는 것 (기본 방식) |
| 직접 오퍼 | 사용자가 업체 프로필·어필 글을 보고 먼저 견적을 요청하는 것 [결정 D-3] |
| 견적서 | 업체가 보내는 제안. 품목, 금액, 일정을 담는다. 채팅에 카드로 표시된다 |
| 확정 요청 / 확정 | 조율이 끝나면 업체가 "확인 및 확정" 버튼을 보내고(확정 요청), 사용자가 눌러서(확정) 그 단계의 업체가 정해진다 |
| 풀스펙 공연장 | 장비와 엔지니어까지 갖춘 공연장. 장비·엔지니어 단계를 건너뛸 수 있다 |
| 통합 청구서 | 모든 단계가 확정된 뒤 사용자에게 한 번에 가는 전체 결제 청구서 |
| 섭외 확정 | 모든 단계가 확정되고 결제가 끝난 상태 |
| 취소 수수료 / 위약금 | 확정·결제 이후 취소할 때 내는 금액. 비율은 POL 영역에서 정한다 |
| 익스프레스 | 공연이 임박한 사용자가 추가 결제하면 공고를 업체 목록 최상단에 올려 주는 유료 옵션 |
| 반려 카운트 | 사용자가 견적을 받은 뒤 공고를 내린 횟수. 업체 화면에 표시된다 |
| 기본 제공 / 추가 제공 | 공간에 원래 있는 장비·인력 / 견적으로 새로 더해지는 장비·인력 |
| 기술 확인 | 공간 측·장비 업체가 반입·전원·연결 등 현장 조건을 확인하고 남기는 기록. 사이트가 자동 판정하지 않는다 |
| 버전 | 요청서·견적서를 수정할 때마다 새로 생기는 번호. 과거 버전은 지우지 않는다 |
| 확인 필요 / 충돌 / 경고 | 자동 검사 결과. 정보 부족 / 조건끼리 어긋남 / 진행은 가능하나 주의 |

## 2. 시스템 개요

### 2.1 서비스 흐름

```
[사용자] 요청서 작성 (STEP1 공연 기본 정보 → STEP2 필요한 것) → 공고 게시
   │
   ▼ ① 공연장 단계 ── 공연장 업체 러브콜(견적서) → 채팅 조율 → 업체 확정 요청 → 사용자 확정
   │                  └ 풀스펙 공연장이면 → "전부 구했어요" 재확인 → ②③ 건너뜀
   ▼ ② 장비 단계 ──── 장비 업체 (배정된 공연장 정보를 보고) 러브콜 → 채팅 → 확정
   │                  └ 공연장이 장비 보유 시 건너뜀
   ▼ ③ 엔지니어 단계 ─ 엔지니어 (공연장·장비 정보를 보고) 러브콜 → 채팅 → 확정
   │                  └ 공연장·장비 견적에 엔지니어 포함 시 건너뜀
   ▼
[사용자] 통합 청구서 → 결제 → 섭외 확정 → 최종 일정·담당표
```

**왜 순서가 정해져 있나**: 장비 업체는 공간의 크기·전원·반입 조건을 알아야 견적을 낼 수 있고, 엔지니어는 공간과 장비를 알아야 한다. 그래서 공간이 항상 먼저 정해진다.

**차별점**: 한 플랫폼에서 공간·장비·인력을 모두 해결한다. 시간은 조금 걸릴 수 있지만, 순서대로 확인하기 때문에 확실하다.

### 2.2 배정 규칙 (중요 절차)

| 경우 | 배정 순서 |
|---|---|
| 1. 아무것도 없음 | 공연장 → 장비 → 엔지니어 |
| 2. 공연장이 이미 정해짐 (외부 예약 포함) | 장비 → 엔지니어 |
| 3. 공연장·장비가 이미 있음 | 엔지니어 |
| 4. 배정된 공연장이 장비·엔지니어를 보유 | 해당 단계 **건너뜀** |

- 사용자가 STEP2에서 "이미 있어요"로 표시한 항목은 그 단계를 만들지 않는다.
- 건너뛰기는 자동으로 하지 않고, 사용자에게 "공연장에 장비가 포함되어 있어요. 장비 단계를 건너뛸까요?" 를 묻는다 (제안).
- 다음 단계 공고가 열리는 시점은 [결정 D-1].

### 2.3 사용자와 업체의 연락 방식

| 방식 | 설명 | 플랫폼 처리 |
|---|---|---|
| 1. 개인 연락 | 사용자가 업체에 전화·문자·카톡으로 직접 연락 | 수수료 없음, 대신 노쇼·예약금 리스크는 사용자 책임. 플랫폼 밖 거래 [결정 D-11] |
| 2. 직접 오퍼 | 사용자가 업체 공고·어필·견적을 보고 견적서를 받아 승인 | 플랫폼 거래 [결정 D-3] |
| **3. 러브콜 (기본)** | 사용자가 올린 공고에 업체가 견적서를 보내고, 사용자가 확인·승인 | **기본 방식** |

### 2.4 사용자 역할

| 역할 | 설명 |
|---|---|
| 방문자 | 로그인하지 않은 사람. 서비스 소개, 공간 목록, 공개 게시판만 볼 수 있다 |
| 사용자 | 요청서·공고 작성, 견적서 확인, 채팅, 단계별 확정, 결제 |
| 업체 | 3단계 입점 → 승인 후 서비스 등록, 공고 확인, 견적서 전송, 채팅, 확정 요청, 기술 확인 |
| 관리자 | 업체 심사, 신고·제재 처리, 거래 이력 확인, 시연 데이터 초기화 |

- 한 계정은 하나의 역할만 가진다. 사용자와 업체는 따로 가입한다 (2026-11-11 결정).
- 업체는 계정 하나에 제공 서비스를 여러 개 등록할 수 있다.

### 2.6 운영 환경과 제약
- 웹 서비스. 데스크톱과 모바일 브라우저 모두 사용 가능 (반응형).
- 기술 스택은 설계 단계에서 결정한다 (`docs/decisions`).
- 모든 화면에 **"포트폴리오 시뮬레이션 — 실제 거래가 아닙니다"** 를 표시한다.
- 실제 결제·대관·파견·정산·위약금 청구는 발생하지 않는다.
- 사이트 하단에는 가상 사업자 정보를 표시하고 "포트폴리오용 가상 정보"를 함께 적는다.

| 네이버 제공 항목 | 동의 설정 | 우리 쓰임 |
|---|---|---|
| 회원 고유 식별값 | 기본 | 계정 연결 키 |
| 이메일 | 필수 동의 | 이메일 |
| 이름 | 필수 동의 | 이름 |
| 휴대전화번호 | 필수 동의 | 전화번호 |
| 출생연도 + 생일 | 선택 동의 | 생년월일 |
| 별명 | 선택 동의 | 닉네임 기본값 |

- 처음 로그인하면 **추가 정보 입력**(FR-AUTH-04)으로 보낸다. 받아온 값은 미리 채운다.
- 수용 기준
  - [ ] 테스터 네이버 계정으로 가입·로그인된다
  - [ ] 선택 동의를 해제해도 추가 정보 화면에서 직접 입력해 가입된다

#### FR-AUTH-03 카카오 가입·로그인 · 권장 (기본값 꺼짐)
- 설정값 `KAKAO_LOGIN_ENABLED` 로 켜고 끈다. 꺼져 있으면 버튼이 보이지 않고 서버도 요청을 거부한다.

| 카카오 제공 항목 | 승인 전 (일반 앱) | 비즈 앱 승인 후 | 우리 쓰임 |
|---|---|---|---|
| 회원번호 | 기본 제공 | 기본 제공 | 계정 연결 키 |
| 닉네임 | 받을 수 있음 | 받을 수 있음 | 닉네임 기본값 |
| 이메일 | - | 동의 시 (**인증된 이메일만** 사용) | 이메일 |
| 이름, 전화번호 | - | 권한 신청 + 검수 | 이름, 전화번호 |
| 출생연도 / 생일 | - | 권한 신청 필요할 수 있음 | 생년월일 |

- 승인 전 기준으로 개발한다 (닉네임만 받고 나머지는 추가 정보 화면에서 입력).
- 수용 기준
  - [ ] 꺼진 상태에서 카카오 로그인 요청은 거부된다
  - [ ] 켠 상태에서 카카오 테스트 계정으로 가입·로그인된다

#### FR-AUTH-04 소셜 가입 추가 정보 입력 · 필수
- 소셜에서 받지 못한 필수 항목과 서비스 전용 항목(가입 목적, 뮤지션 유형, 가입 경로), **우리 서비스 약관 동의**를 받는다.
  - 소셜 쪽 동의는 정보 제공 동의일 뿐이므로 우리 약관 동의는 따로 받는다.
- 비밀번호는 받지 않는다.
- 수용 기준
  - [ ] 소셜에서 받은 값은 미리 채워지고 수정할 수 있다
  - [ ] 약관 동의 없이 가입이 완료되지 않는다

#### FR-AUTH-05 소셜 계정 연결 규칙 · 필수
- 회원 정보와 소셜 연결 정보(provider, 고유 식별값, 연결 일시)를 분리해 저장한다.
- **같은 이메일이라도 자동으로 합치지 않는다.** 연결은 로그인한 상태에서만 한다.
- 탈퇴 시 소셜 연결 끊기도 처리한다. 카카오의 연결 끊기 알림을 받는 주소를 둔다.
- 수용 기준
  - [ ] 이메일 계정과 같은 이메일의 네이버 계정으로 로그인해도 기존 계정에 들어가지 않는다

#### FR-AUTH-06 로그인·로그아웃 · 필수
- 로그인 후 역할별 첫 화면으로 이동한다: 사용자 = 내 공연 / 업체 = 공고 목록 (승인 전에는 심사 상태) / 관리자 = 심사 대기
- 로그인 5회 연속 실패 시 10분간 제한 (제안).
- 수용 기준
  - [ ] 역할별로 다른 첫 화면이 열린다
  - [ ] 로그아웃 후 뒤로 가기로 이전 화면의 개인 정보가 보이지 않는다

#### FR-AUTH-07 역할 기반 접근 제한 · 필수
- 모든 기능은 2.5 권한표를 따르고 **서버에서 검사한다.**
- 권한 없는 요청은 데이터 존재 여부도 알 수 없게 응답한다 (제안: 404).
- 수용 기준
  - [ ] 다른 사용자의 공연·채팅방 ID로 조회하면 볼 수 없다
  - [ ] 업체가 다른 업체의 견적서 ID로 조회하면 거부된다
  - [ ] 심사 중인 업체가 견적서 전송 요청을 직접 보내도 거부된다

#### FR-AUTH-08 시연 계정 전환 · 권장
- 테스트 환경에서만, 시연 계정(사용자, 업체 A~G, 관리자)으로 빠르게 로그인한다. 시연 계정은 이메일 계정이다.
- 수용 기준
  - [ ] 운영 설정에서는 전환 기능이 보이지도 동작하지도 않는다

### 3.2 업체 입점·심사 (SUP) — 2번

업체는 **이메일 가입만** 한다. 3단계를 거쳐야 공고를 볼 수 있다.

#### FR-SUP-01 1단계: 계정 가입 · 필수

| 항목 | 필수 |
|---|---|
| 이메일, 비밀번호, 비밀번호 확인 | O |

| 이용약관 동의, 개인정보 수집·이용 동의 | O |
| 마케팅 수신 동의 | - |

- 회사 공용 이메일 사용을 안내한다 (담당자 퇴사 대비).

#### FR-SUP-02 2단계: 입점 신청 (사업자 정보) · 필수

| 항목 | 개인 (프리랜서) | 개인사업자·법인 | 규칙 |
|---|---|---|---|
| 사업자 유형 | O | O | |
| 상호명 | O (활동명) | O | |
| 대표자 성명 | O (본인) | O | |
| 사업자등록번호 | - | O | 10자리 형식·체크섬 검증. 국세청 조회는 후속 |
| 사업자등록증 사본 | - | O | 시연은 가상 이미지 |
| 사업장 주소 | 활동 지역 | O | |
| 대표 전화 | O | O | |
| 통신판매업 신고번호 | - | - | 선택. "해당 없음" 선택 가능 |

- 신청하면 `심사 중`. 사업자 정보는 관리자만 본다 (사용자에게 비공개).
- 수용 기준
  - [ ] 개인을 고르면 사업자등록번호·등록증 칸이 사라진다
  - [ ] 체크섬이 틀린 사업자등록번호는 저장되지 않는다

#### FR-SUP-03 관리자 심사 · 필수
- 관리자가 `승인` / `반려`(사유 필수) / `정지`(사유 필수)를 처리한다.
- 상태: `심사 중` → `승인` / `반려` → (재신청) `심사 중`, `승인` ↔ `정지`
- 정지된 업체는 견적서를 보낼 수 없고, 진행 중인 채팅방에 "정지된 업체" 표시가 붙는다.
- 수용 기준
  - [ ] 승인되면 3단계 서비스 등록과 공고 목록이 열린다
  - [ ] 반려 사유가 업체 화면에 보이고 수정 후 재신청할 수 있다

#### FR-SUP-04 3단계: 서비스 등록 · 필수 (승인 후)

**공통**: 제공 서비스 부문(복수), 활동 지역(시·도 복수), 업체 소개, 업체 사진(선택), 영업배상책임보험 가입 여부(선택) [자문]

| 부문 | 항목 | 필수 |
|---|---|---|
| 공간 | FR-SPACE-01 공간 등록으로 이어짐 | O |
| 음향 장비 | 보유 장비 분류 (음향 / 화면 / 악기 / 조명) | O |
| | 분류별 주요 품목·수량 [자문: 표준 품목] | - |
| 설치·철수 | 기본 설치·철수 소요 시간 (분) (제안) | O |
| 현장 운영 (엔지니어) | 가능 작업 (FR-REQ-02의 엔지니어 작업 목록), 경력 연수, 밴드 공연 경험 (제안) | - |

- 업체는 본인 정보만 수정할 수 있다.

### 3.3 공간 (SPACE) — 등록 2번 / 탐색 1번

#### FR-SPACE-01 공간 등록 · 필수
- 입력 항목
  - 이름, 소재지(시·도, 시·군·구, 주소), 공간 유형(전문 공연장 / 복합문화공간 / 루프탑 / 정원 / 창고 / 기타)
  - **최대 수용 인원** (1~500)
  - **입실 가능 시각, 퇴실 마감 시각**
  - 대관료 기준 금액
  - **기본 제공 장비** (분류·품목·수량), **기본 제공 인력** (상주 엔지니어 유무) → 풀스펙 여부 판단에 사용
  - **공간 조건** (사용자 STEP2 조건과 같은 항목): 밴드 공연 가능, 외부 음향 장비 반입 가능, 외부 엔지니어 허용, 대기실, 무대 단상, 주차
  - 공연법상 공연장 등록 여부 (선택) [자문], 사진 (선택)
- 비워 둔 공간 조건은 `미확인`으로 저장한다.
- 수용 기준
  - [ ] 수용 인원 501 이상은 저장되지 않는다
  - [ ] 퇴실 마감이 입실 시각보다 빠르면 저장되지 않는다

#### FR-SPACE-02 과거 조건 보존 · 필수
- 공연장이 배정(확정)되는 순간 그 시점의 공간 정보를 공연에 복사해 보관한다 (스냅샷).
- 원본을 수정해도 이미 확정된 공연의 조건은 바뀌지 않는다.
- 수용 기준
  - [ ] 공간의 기본 마이크 수를 2 → 1로 바꿔도 확정된 공연에는 2로 남아 있다

#### FR-SPACE-03 공간 탐색 · 필수
- 누구나 공간 목록을 본다. 필터: 지역, 수용 인원, 공간 유형, 공간 조건. 정렬: 대관료, 수용 인원.
- 날짜 필터는 예약 가능을 보장하지 않는다. "업체 확인 전"을 표시한다.
- 직접 오퍼를 MVP에 넣으면 공간 상세에 "견적 요청하기" 버튼을 둔다 [결정 D-3].
- 수용 기준
  - [ ] 광주 / 80명 / 밴드 공연 가능으로 필터하면 시연 공간 A·B·C가 나온다

### 3.4 공연 요청서·공고 (REQ) — 1번

#### FR-REQ-01 STEP1 공연 기본 정보 · 필수

| 항목 | 필수 | 규칙 |

  - [ ] 리허설이 공연 시작보다 늦으면 저장되지 않는다
  - [ ] 대표 시연 요청 "토요일 19~21시, 80명, 리허설 17시"를 입력할 수 있다

#### FR-REQ-02 STEP2 무엇이 필요하신가요 · 필수
- 공연장 / 장비 / 엔지니어 각각에 **"필요해요" 토글**을 둔다. **기본값은 모두 켜짐.**
  - 끄면("이미 있어요") 그 항목의 입력 칸이 사라지고, 배정 단계에서도 빠진다 (2.2 배정 규칙).
  - 공연장을 끈 경우: 이미 확보한 공간의 이름, 주소, 입실·퇴실 시각, 기본 장비를 입력한다 (장비·엔지니어 업체가 볼 정보).
- 각 항목 오른쪽에 **"업체 제안 받기"** 버튼을 둔다. 필수 정보만 받고 나머지는 업체 견적으로 받는다.

**공연장이 필요할 때**

| 항목 | 필수 |
|---|---|
| 공간 유형 (전문 공연장 / 복합문화공간 / 루프탑 / 정원 / 창고 / 상관없음 / 기타-직접 입력) | O |
| 필요 수용 인원 | O |
| 대관 예산 | - |
| 입실 희망 시각, 퇴실 시각 | - (업체 제안 받기 가능) |
| 꼭 필요한 조건 (체크박스): 밴드 공연 가능, 외부 음향 장비 반입 가능, 외부 엔지니어 허용, 대기실, 무대 단상, 주차 | - |
| 업체에게 추가 요청사항 | - |

**장비가 필요할 때**

| 항목 | 필수 |
|---|---|
| 원하는 장비: **기본값 없음.** "+ 장비 추가" 버튼으로 이름·수량을 자유롭게 입력. 어려우면 "업체 제안 받기" | - |
| 필요한 서비스 (체크박스): 운반, 설치 및 철수 | - |
| 장비 예산 | - |
| 이미 가지고 있는 장비: "+ 장비 추가"로 자유 입력. 자세히 적도록 안내 (예: "드럼 세트 — 심벌 포함, 킥 페달 1") | - |

**엔지니어가 필요할 때**

| 항목 | 필수 |
|---|---|
| 해 줘야 할 작업 (체크박스, 복수) — 아래 목록 | O (1개 이상) |
| 원하는 조건 (체크박스): 밴드 공연 경험, 리허설 참여 가능, 철수까지 함께, 기타(직접 입력) | - |

엔지니어 작업 목록 (팀 결정 2개 + 제안, 최종 목록은 [결정 D-17]):
- 메인 음향 (FOH 믹싱) — 팀 결정
- 설치 및 철수 보조 — 팀 결정
- 사운드체크·리허설 진행 (제안)
- 모니터 믹싱 (무대 위 연주자용 소리) (제안)
- 무선 마이크 채널·배터리 관리 (제안)
- 녹음 / 라이브 스트리밍 음향 송출 (제안)
- 공연 중 장비 문제 대응 (제안)

- 수용 기준
  - [ ] 장비 토글을 끄면 장비 입력 칸이 사라지고 배정 단계에 장비가 생기지 않는다
  - [ ] 장비 칸에 아무 기본값도 들어 있지 않다
  - [ ] 엔지니어가 필요한데 작업을 하나도 고르지 않으면 다음으로 넘어가지 않는다

#### FR-REQ-03 공고 게시 · 필수
- 게시하면 **첫 배정 단계**의 업체에게만 공고가 보인다 (2.2). 예: 공연장이 필요하면 공간 부문 업체만.
- 공고에는 사용자의 연락처 등 개인정보를 노출하지 않는다. 닉네임, 반려 카운트, 이용 횟수만 보인다 (POL).
- 공고 노출 범위(지역·부문 필터 여부) [결정 D-4].
- 공고 마감 방식 [결정 D-5].
- 수용 기준
  - [ ] 공연장 단계 공고는 장비 업체·엔지니어에게 보이지 않는다
  - [ ] 심사 중인 업체에게는 보이지 않는다

#### FR-REQ-04 요청서 수정과 버전 · 필수
- 게시 후 수정하면 새 버전이 생기고 이전 버전은 남는다. 견적서를 보낸 업체에게 "조건 변경 (v1 → v2)" 과 바뀐 항목을 보여준다.
- 이미 확정된 단계에 영향을 주는 수정(예: 리허설 시각 변경)이면 그 단계 업체에게 **재확인**을 요청한다. 재확인 전에는 결제할 수 없다.
- 섭외 확정 후에는 수정할 수 없다.
- 수용 기준
  - [ ] 리허설 17시 → 16시 변경 시 v2가 생기고, 확정된 장비 업체에게 재확인 요청이 간다

#### FR-REQ-05 내 공연 현황 · 필수
- 공연별로 현재 배정 단계, 단계별 상태(모집 중 / 조율 중 / 확정 / 건너뜀), 받은 견적서 수, 다음 할 일을 보여준다.
- 수용 기준
  - [ ] "공연장 확정 ✓ → 장비 조율 중 (견적 2건) → 엔지니어 대기" 처럼 단계가 한눈에 보인다

### 3.5 순차 배정 (ASSIGN) — 1번 + 3번

#### FR-ASSIGN-01 단계 진행 · 필수
- 단계는 공연장 → 장비 → 엔지니어 순서로만 진행한다. 앞 단계가 확정되거나 건너뛰어져야 다음 단계 공고가 열린다.
- 다음 단계를 자동으로 열지, 사용자가 누를 때 열지 [결정 D-1].
- 단계 상태: `대기` → `모집 중` → `조율 중`(채팅 진행) → `확정` / `건너뜀`
- 수용 기준
  - [ ] 공연장이 확정되기 전에는 장비 업체에게 공고가 보이지 않는다
  - [ ] 공연장 확정 후 장비 단계가 열린다

#### FR-ASSIGN-02 단계별 업체에게 전달되는 정보 · 필수

| 업체 | 받는 정보 |
|---|---|
| 공연장 업체 | 공연 기본 정보(STEP1), 원하는 공연장 조건 |
| 장비 업체 | 공연 기본 정보, **배정된 공연장 스펙·정보**, 필요한 장비, 이미 가진 장비 |
| 엔지니어 | 공연 기본 정보, 배정된 공연장 스펙·정보, **배정된 장비 스펙·정보**, 해 줘야 할 작업, 원하는 조건 |

- 수용 기준
  - [ ] 장비 업체 공고 상세에 배정된 공연장의 입실 시각·기본 장비·전원 정보가 보인다

#### FR-ASSIGN-03 풀스펙 공연장과 "전부 구했어요" · 필수
- 공연장 견적서에 장비·엔지니어가 포함되어 있으면, 사용자가 확정할 때 "장비·엔지니어 단계를 건너뛸까요?"를 묻는다.
- 사용자가 직접 업체와 다 해결했다면 **"전부 구했어요"** 를 누를 수 있다. 이때 **팝업으로 한 번 더 확인**하고, 이후 일정·장비 문제의 책임은 사용자에게 있음을 안내한다.
- 수용 기준
  - [ ] "전부 구했어요"를 누르면 재확인 팝업이 뜨고, 확인 후 남은 단계가 `건너뜀`이 된다
  - [ ] 시연 공간 A(풀스펙)를 확정하면 장비·엔지니어 단계 건너뛰기를 묻는다

### 3.6 견적서 (QUOTE) — 2번

#### FR-QUOTE-01 공고 목록·상세 (업체) · 필수
- 승인된 업체는 **자기 부문의 현재 단계 공고**만 본다.
- 정렬: **익스프레스 공고 최상단**, 그다음 공연일 임박 순 (POL-01).
- 사용자 닉네임 옆에 반려 카운트와 이용 횟수가 표시된다 (POL-02, POL-03).
- 수용 기준
  - [ ] 다른 업체가 보낸 견적서는 어디에서도 보이지 않는다

#### FR-QUOTE-02 견적서 작성·전송 (러브콜) · 필수
- 업체가 공고에 견적서를 보내면 **사용자의 채팅 목록에 그 업체와의 채팅방이 생기고, 견적서 카드가 올라온다** (CHAT).
- 한 공고에 업체당 견적서 여러 개 가능 여부 [결정 D-6].
- 입력 항목
  - 품목: 이름, 분류, 수량, 단가, 금액
  - 인력: 역할, 인원, 근무 시작·종료 시각
  - 일정: 입실 가능 시각(공간), 설치 시작·소요 시간(장비), 철수 소요 시간
  - 금액: 항목별 금액, **최종 합계**, 별도 비용 / 포함 여부: 장비 포함, 엔지니어 포함, 설치·철수 포함, 운반 포함
  - 견적 유효기한, 기술 확인 메모
- 최종 합계는 서버에서 다시 계산한다. 금액은 원 단위 정수.
- 부가세 포함 여부 [결정 D-14].
- 수용 기준
  - [ ] D 사운드가 "추가 마이크 2, 밴드 음향, 설치·철수, 엔지니어 포함, 125만 원, 설치 90분" 견적서를 보낼 수 있다
  - [ ] 합계를 조작한 요청은 거부된다
  - [ ] 공연장 단계가 아닌데 공간 견적서를 보내면 거부된다

#### FR-QUOTE-03 견적서 수정·철회 · 필수
- 채팅 조율 중 업체는 견적서를 **실시간으로 수정**할 수 있다. 수정하면 새 버전이 생기고 채팅에 "견적서가 수정되었어요 (v1 → v2)" 카드가 올라온다.
- 확정된 견적서는 수정할 수 없다. 확정 후 변경이 필요하면 새 견적서 → 재확정.
- 수용 기준
  - [ ] D 견적서 v1(125만)이 v2(135만)로 바뀌어도 v1 기록이 남는다

### 3.7 채팅 (CHAT) — 3번 + 4번

#### FR-CHAT-01 채팅방 · 필수
- 업체가 견적서를 보내면 **공고 × 업체** 단위 1:1 채팅방이 생긴다. 사용자가 먼저 "채팅 시작하기"를 눌러야 대화가 열린다 (제안).
- 메시지 종류: 텍스트, 견적서 카드, 확정 요청 카드, 시스템 안내 [결정 D-7: 사진·파일]
- 새 메시지 알림을 표시한다 (사이트 안 알림 배지).
- 실시간 방식 [결정 D-7].
- 수용 기준
  - [ ] 사용자는 공고별로 업체 채팅방 목록을 본다
  - [ ] 다른 사람의 채팅방은 열 수 없다

#### FR-CHAT-02 확정 요청과 확정 · 필수
- 조율이 끝나면 **업체가 "확인 및 확정" 요청 카드**를 보낸다. 카드에는 최종 견적서 버전이 들어간다.
- 사용자는 견적서를 한 번 더 읽고 카드 아래 **"확인 및 확정"** 버튼을 누른다. → 그 단계 `확정`.
- 같은 단계에서 다른 업체가 확정되면 나머지 채팅방에 "다른 업체로 확정되었어요"를 안내한다.
- 한 단계에 업체 하나만 확정된다 (동시 확정 방지).
- 수용 기준
  - [ ] 사용자가 확정하면 그 단계가 확정되고 다음 단계가 열린다 (D-1에 따라)
  - [ ] 확정 요청 후 견적서가 수정되면 이전 확정 요청은 무효가 된다
  - [ ] 같은 단계에서 두 업체를 동시에 확정할 수 없다

#### FR-CHAT-03 연락처·외부 거래 보호 · 필수
- 확정 전 채팅에서는 전화번호·계좌번호·외부 메신저 아이디로 보이는 내용에 **경고 문구**를 띄운다 (제안) [결정 D-11].
- 사용자가 STEP1에서 전화번호를 남긴 경우의 공개 시점 [결정 D-11].
- 채팅 신고 기능을 둔다. 관리자는 신고된 채팅방만 볼 수 있다.

### 3.8 자동 검사 (CHK) — 3번

순차 배정이므로 **단계마다** 앞 단계에서 확정된 정보와 견적서를 비교한다. 요청서나 견적서가 바뀌면 다시 검사한다.
결과: `통과` / `확인 필요` / `충돌` / `경고`

| ID | 단계 | 검사 | 규칙 | 결과 |
|---|---|---|---|---|
| CHK-01 | 공연장 | 인원 | 예상 관객 ≤ 수용 인원 | 넘으면 `충돌` |
| CHK-02 | 공연장 | 준비 시간 | 입실 가능 시각 + 예상 설치 시간 ≤ 리허설 시작 (예상 설치 시간 기본값 (제안) [자문]) | 부족하면 `경고` "설치 시간 부족 가능" |
| CHK-03 | 공연장 | 조건 | STEP2 꼭 필요한 조건 ⊂ 공간 조건 | 없으면 `충돌`, 미확인이면 `확인 필요` |
| CHK-04 | 장비 | 입실 → 설치 | 공연장 입실 ≤ 설치 시작 | 아니면 `충돌` |
| CHK-05 | 장비 | 설치 → 리허설 | 설치 시작 + 설치 소요 ≤ 리허설 시작 | 아니면 `충돌` (늦는 시간 표시) |
| CHK-06 | 장비 | 수량 | 공연장 기본 + 이미 가진 장비 + 견적 장비 ≥ 원하는 장비 (품목별) | 부족하면 `경고` |
| CHK-07 | 장비 | 철수 → 퇴실 | 공연 종료 + 철수 소요 ≤ 퇴실 마감 | 아니면 `충돌` |
| CHK-08 | 엔지니어 | 근무 시간 | 근무가 리허설 시작 ~ 공연 종료(철수 포함 조건 시 철수 끝)를 포함 | 아니면 `충돌` |
| CHK-09 | 엔지니어 | 중복 | 앞 단계 견적에 엔지니어가 포함되어 있음 | `경고` + 단계 건너뛰기 제안 |
| CHK-10 | 공통 | 예산 | 견적 금액 > 해당 예산 | `경고` |
| CHK-11 | 공통 | 정보 누락 | 검사에 필요한 값이 없음 | `확인 필요` |
| CHK-12 | 공통 | 버전 | 견적서가 이전 요청서 버전 기준 | `경고` |

- `충돌`이 있는 견적서는 확정할 수 없다. `경고`·`확인 필요`는 확정할 수 있지만 사용자에게 다시 묻는다 (제안).
- 소리 크기, 장비 호환성, 현장 안전은 자동 판정하지 않는다 (TECH).
- 수용 기준 (대표 시나리오)
  - [ ] 공연장 단계: B(입실 17:00, 리허설 17:00) → CHK-02 `경고` "설치 시간 0분", C(입실 15:00) → `통과`
  - [ ] 장비 단계(공연장 C): D 설치 90분 → 16:30 완료 → CHK-05 `통과`
  - [ ] 장비 단계(만약 공연장 B): D → 18:30 완료 → CHK-05 `충돌` "90분 늦음"
  - [ ] D에 엔지니어 포함 → 엔지니어 단계에서 CHK-09 `경고` + 건너뛰기 제안
  - [ ] 리허설을 16시로 바꾸면 D가 다시 검사되어 `충돌`, D 수정 견적(15:45 완료) 후 `통과`

#### FR-CHK-01 단계별 견적 비교 화면 · 필수 (대표 화면)
- 현재 단계에 온 견적서들을 나란히 보여준다: 금액, 포함 항목, 일정 타임라인, 검사 결과, 기술 확인 상태.
- 공연장 단계에서는 풀스펙 공연장(장비·엔지니어 포함)과 공간만 제공하는 공연장을 함께 비교하는 방법 [결정 D-8].
- 가격과 검사 결과를 따로 표시한다. 싸다고 가능한 것이 아님을 보여준다.
- 수용 기준
  - [ ] 공연장 단계에서 A(400만, 풀스펙) / B(40만, 경고) / C(50만, 통과)가 한 화면에 보인다

### 3.9 기술 확인 (TECH) — 3번

#### FR-TECH-01 기술 확인 항목과 답변 · 필수
- 장비 단계부터, 배정된 공연장과 장비 업체가 확인할 항목을 만든다 [자문: 최종 목록]
  - 외부 장비 반입 / 외부 엔지니어 허용 / 전원 (용량·위치) / 반입 동선 / 설치 공간 / 연결 방식 / 소음 제한 / 야외 조건
- 각 항목 담당자가 `확인됨` / `조건부` / `불가` + 메모. 담당자, 일시, 대상 버전을 저장한다.
- 요청서·견적서가 새 버전이 되면 `재확인 필요`. `불가`가 있으면 그 견적서는 `충돌`.
- 수용 기준
  - [ ] 공연장 C와 장비 D가 각자 담당 항목에만 답변할 수 있다

### 3.10 결제·취소 (PAY) — 4번

#### FR-PAY-01 통합 청구서 · 필수
- **모든 필요 단계가 확정(또는 건너뜀)되면** 사용자에게 **통합 청구서**가 한 번에 간다.
  - 단계별 업체, 확정 견적서 버전, 금액, 합계, 별도 비용, 플랫폼 수수료 표시 여부 [결정 D-18]
- 결제 흐름 [결정 D-9]: 통합 청구서 한 번 결제 / 업체별로 업체가 결제 요청 (목산님 의견)
- 수용 기준
  - [ ] 공연장 C 50만 + 장비 D 135만 = 185만 원 통합 청구서가 생긴다
  - [ ] 확정되지 않은 단계가 있으면 청구서가 생기지 않는다

#### FR-PAY-02 결제 · 필수
- 결제 방식 [결정 D-10]. 화면에 "테스트 결제 — 실제 청구되지 않습니다".
- 결제 금액은 서버가 확정 견적서 스냅샷으로 계산한다.
- 결제 직전에 다시 검사: 모든 단계 확정, 재확인 대기 없음, 견적서 버전이 확정 당시와 같음.
- 결제 성공은 서버에서 확인한 뒤에만 `섭외 확정`. 실패·취소는 확정하지 않는다.
- 같은 결제 응답은 한 번만 반영한다. 버튼을 두 번 눌러도 한 번만 결제된다.
- 수용 기준
  - [ ] 금액을 조작한 결제 요청은 거부된다
  - [ ] 같은 성공 응답을 두 번 보내도 결제 기록이 하나다

#### FR-PAY-03 취소 수수료·위약금 · 필수

| 시점 | 사용자가 내는 금액 | 받는 쪽 |
|---|---|---|
| 모든 업체 확정 후 결제 단계에서 취소 | 취소 수수료 **10%** | [결정 D-12] |
| 결제 후 ~ D-3 | [결정 D-12] | |
| **D-2** | 위약금 **50%** | 업체 |
| **D-1** | 위약금 **70%** | 업체 |
| **D-0 (당일)** | 위약금 **100%** | 업체 |

- 업체 사정으로 취소되는 경우의 처리 [결정 D-12].
- 위약금 계산과 환불은 시뮬레이션으로 기록만 한다 (실제 청구 없음).
- 수용 기준
  - [ ] D-1에 취소하면 70%가 위약금으로, 나머지가 환불 예정액으로 계산된다
  - [ ] 업체별 위약금 배분이 계산되어 업체 화면에 보인다

#### FR-PAY-04 섭외 확정·최종 담당표 · 필수
- 결제 후 사용자와 확정된 업체들이 같은 최종 담당표를 본다: 업체별 담당 범위, 금액, 일정(입실 → 설치 → 리허설 → 공연 → 철수 → 퇴실), 기술 확인 요약.
- 확정되지 않은 업체(경쟁 업체)는 볼 수 없다.

### 3.11 운영 정책 (POL) — 4번

#### FR-POL-01 익스프레스 · [결정 D-13: MVP 포함 여부]
- 공연이 임박한 사용자가 추가 결제하면 공고가 업체 목록 **최상단**에 표시된다. 익스프레스끼리는 공연일 임박 순.
- 결제 후 **24시간 안에 업체 연락(컨택)이 없으면 익스프레스 금액 전액 환불**.
- 환불 후 공고를 일방적으로 내리지 않고 사용자에게 묻는다: "다시 결제해서 올릴까요? / 그만할까요?"
- 수용 기준
  - [ ] 익스프레스 공고가 일반 공고보다 위에 보인다
  - [ ] 24시간 동안 컨택이 없으면 환불 처리되고 사용자에게 선택지가 뜬다

#### FR-POL-02 반려 카운트 · 필수
- 사용자가 견적서를 받은 공고를 내리면 카운트가 오른다. 업체 화면에서 닉네임 옆에 "N회 반려"로 표시한다.

| 경우 | 카운트 | 제한 |
|---|---|---|
| 업체 견적을 보고 **채팅을 시작한 뒤** 공고를 내림 | 채팅 반려 +1 | **5회 이상**: 공고마다 24시간 후 등록 가능 |
| 업체 견적을 보고 **채팅을 시작하지 않고** 공고를 내림 | 미응답 반려 +1 | **10회 이상**: 공고마다 24시간 후 등록 가능 |

- 카운트 초기화·감소 규칙 [결정 D-19].
- 수용 기준
  - [ ] 채팅 반려 5회째 이후 새 공고는 마지막 내림 시각 + 24시간 이후에만 게시된다

#### FR-POL-03 단골 표시 · 권장
- 업체 화면에서 사용자 닉네임 옆에 "우리 서비스 N번 이용"을 표시한다 (섭외 확정 건수).

#### FR-POL-04 플랫폼 외 거래·계약 위반 제재 · 필수
- 견적서를 받은 뒤 사용자와 업체가 플랫폼 밖에서 연락해 계좌이체하거나, 견적서·계약과 실제 이행 내용이 다르면 **계약 위반**으로 처리한다.
- 제재 종류: 위약금, 전액 환불, 신고, 이용 정지 (사용자·업체 모두)
- 감지 방법과 제재 단계 [결정 D-11]. MVP에서는 **신고 → 관리자 확인 → 제재 기록**까지 (제안).
- 참고 사례: 당근페이 등 플랫폼 내 결제 유도 정책

### 5.2 상태 흐름

**공연**
```
작성 중 → 공고 게시 → 배정 진행 중 → 결제 대기 → 섭외 확정 → 공연 완료
              │            │              │            │
              └────────────┴──── 취소 ────┴────────────┘ (시점에 따라 수수료·위약금)
```

**배정 단계 (공연장 / 장비 / 엔지니어 각각)**: `대기` → `모집 중` → `조율 중` → `확정` / `건너뜀`, `확정` → (조건 변경 시) `재확인 필요` → `확정`
**업체**: `심사 중` → `승인` / `반려`, `승인` ↔ `정지`
**견적서**: `전송됨` → `수정됨`(새 버전) / `철회` / `만료` / `확정`
**확정 요청**: `대기` → `확정` / `무효`(견적서 수정·다른 업체 확정)
**결제 시도**: `진행 중` → `성공` / `실패` / `취소`
