## 1. 문서 개요

### 1.1 목적
이 문서는 공연 공간·음향 섭외 플랫폼 **STAGE DUCK**의 **MVP 범위를 개발·테스트할 수 있는 수준으로** 정의한다.
각 기능은 ID, 설명, 처리 규칙, 예외, 수용 기준을 가진다. 설계·개발·테스트는 이 문서의 ID를 기준으로 추적한다.

### 1.2 범위
| 구분 | 이 문서에서 다루는 수준 |
|---|---|
| MVP | **상세** (기능별 규칙과 수용 기준) |
| 후속 기능 | 목록만 (9장) |

MVP는 **포트폴리오용 시뮬레이션**이다. 공간·업체·엔지니어·가격은 모두 가상 데이터이고, 결제는 테스트 결제로만 동작한다.

### 1.3 표기 규칙
- **우선순위**: `필수` = MVP 완료 조건 / `권장` = 일정이 허락하면 MVP에 포함 / `선택` = 후속
- **(제안)**: 아직 확정되지 않은 수치나 정책. 검토 후 확정하면 표시를 지운다.
- **[미정]**: 정보가 없어 비워 둔 값. 10장 미결정 사항에 모아 둔다.
- **[자문]**: 현장 전문가(목산님) 확인이 필요한 항목.
- 기능 ID: `FR-<영역>-<번호>`, 비기능 ID: `NFR-<영역>-<번호>`

### 1.4 영역 코드와 담당

| 코드 | 영역 | 담당 (총계획서 7장) |
|---|---|---|
| AUTH | 계정·로그인·역할 | 공통 |
| SUP | 공급자 입점·심사 | 2. 공급자 등록·견적 |
| SPACE | 공간 등록·탐색 | 등록: 2 / 탐색·선택: 1 |
| REQ | 공연 요청·공고 | 1. 공연 요청·공간 선택 |
| QUOTE | 견적 작성·수정 | 2. 공급자 등록·견적 |
| CMP | 조합 비교·자동 검사 | 3. 견적 비교·구성 확인 |
| TECH | 기술 확인 기록 | 3. 견적 비교·구성 확인 |
| CONF | 업체 최종 수락 | 4. 업체 수락·결제·확정 |
| PAY | 테스트 결제·섭외 확정 | 4. 업체 수락·결제·확정 |
| ADMIN | 관리자 기능 | 2(심사) + 4(거래 이력) |
| DEMO | 시연 데이터 | 공통 |

### 1.5 용어 정의

| 용어 | 정의 |
|---|---|
| 주최자 | 공연을 준비하며 공간·장비·인력을 찾는 사용자 (밴드, 극단, 교회, 학원 등) |
| 공급자 | 공간·장비·인력을 제공하는 사용자. 공간 운영자, 음향업체, 엔지니어를 통칭 |
| 제공 서비스 | 공급자가 제공하는 부문. `공간` / `음향 장비` / `설치·철수` / `현장 운영(엔지니어)`. 한 공급자가 여러 부문을 가질 수 있다 |
| 공연 요청서 | 주최자가 작성하는 공연 조건 문서 (일시, 인원, 리허설, 필요 장비 등) |
| 공고 | 게시된 공연 요청서. 승인된 공급자가 보고 견적을 제출한다 |
| 견적 | 공급자가 공고에 대해 제출하는 제안. 품목, 금액, 일정을 포함한다 |
| 전체 패키지 | 공간·장비·인력을 모두 포함한 한 공급자의 견적 (예: A 라이브홀) |
| 조합 | 주최자가 고른 견적들의 묶음 (예: C 공간 + D 음향). 전체 패키지 하나도 조합이다 |
| 기본 제공 | 공간에 원래 갖춰진 장비·인력 (예: 유선 보컬마이크 2개) |
| 추가 제공 | 견적으로 새로 더해지는 장비·인력 |
| 기술 확인 | 공간 측·음향업체가 반입·전원·연결 등 현장 조건을 확인하고 남기는 기록. 사이트가 자동 판정하지 않는다 |
| 업체 확인(수락) | 조합에 포함된 각 공급자가 최종 금액·범위·일정에 동의하는 것 |
| 섭외 확정 | 모든 업체가 수락하고 테스트 결제가 성공한 상태 |
| 버전 | 요청서·견적을 수정할 때마다 새로 생기는 번호. 과거 버전은 지우지 않는다 |
| 확인 필요 | 판정에 필요한 정보가 없어서 시스템이 통과·충돌을 결정할 수 없는 상태 |
| 충돌 | 입력된 조건끼리 어긋나는 상태 (예: 설치 완료가 리허설 시작보다 늦음) |

## 2. 시스템 개요

### 2.1 서비스 흐름

```
[주최자] 공연 요청서 작성 → 공간 후보 선택(또는 확보한 공간 입력) → 공고 게시
                                                         │
[공급자] (승인된 공급자) 공고 목록 → 견적 제출 ────────────┘
                                                         │
[주최자] 받은 견적 비교 → 조합 선택 ← 자동 검사(수량·시간·중복) + 기술 확인 상태
                                                         │
[공급자] 조합에 포함된 업체별 최종 수락 / 거절
                                                         │
[주최자] 테스트 결제 → 섭외 확정 → 최종 일정·담당표
```

### 2.2 사용자 역할

| 역할 | 설명 |
|---|---|
| 방문자 | 로그인하지 않은 사용자. 서비스 소개와 공간 목록만 볼 수 있다 |
| 주최자 | 공연 요청서 작성·공고 게시, 견적 비교, 조합 선택, 결제 |
| 공급자 | 입점 신청 → 승인 후 공간·서비스 등록, 공고 확인, 견적·기술 확인·수락 |
| 관리자 | 공급자 심사, 게시 정보·거래 이력 확인, 시연 데이터 초기화 |

한 계정은 하나의 역할을 가진다 (제안). 공급자는 계정 하나에 제공 서비스를 여러 개 등록할 수 있다.

### 2.3 권한표

| 기능 | 방문자 | 주최자 | 공급자(심사 중) | 공급자(승인) | 관리자 |
|---|---|---|---|---|---|
| 공간 목록·상세 보기 | O | O | O | O | O |
| 공연 요청서 작성·수정 | - | 본인 것 | - | - | 보기만 |
| 공고 목록 보기 | - | 본인 것 | - | O | O |
| 견적 제출·수정·철회 | - | - | - | 본인 것 | 보기만 |
| 견적 보기 | - | **본인 공연에 온 것** | - | **본인 것만** | O |
| 공간·서비스 등록·수정 | - | - | - | 본인 것 | 보기·숨김 |
| 기술 확인 답변 | - | - | - | 본인이 포함된 조합 | 보기만 |
| 업체 최종 수락·거절 | - | - | - | 본인이 포함된 조합 | **불가** |
| 테스트 결제 | - | 본인 공연 | - | - | **불가** |
| 공급자 심사 | - | - | - | - | O |
| 시연 데이터 초기화 | - | - | - | - | O (테스트 환경만) |

- 관리자는 당사자의 수락이나 결제를 **대신 확정하지 않는다.**
- 공급자는 **다른 공급자의 견적을 볼 수 없다.**

### 2.4 운영 환경과 제약
- 웹 서비스. 데스크톱과 모바일 브라우저 모두 사용 가능 (반응형).
- 기술 스택은 설계 단계에서 결정한다 (`docs/decisions`).
- 모든 화면 상단 또는 하단에 **"포트폴리오 시뮬레이션 — 실제 거래가 아닙니다"** 를 표시한다.
- 실제 결제·대관·파견·정산은 발생하지 않는다.

## 3. 기능 요구사항 (MVP)

### 3.1 계정 (AUTH) — 공통

#### FR-AUTH-01 회원 가입 · 필수
- 이메일과 비밀번호로 가입한다 (제안). 가입할 때 역할을 **주최자 / 공급자** 중에서 고른다.
- 관리자 계정은 가입 화면에서 만들 수 없다. 시드 데이터로만 생성한다.
- 비밀번호 규칙: 8자 이상, 영문·숫자 포함 (제안).
- 공급자로 가입하면 입점 신청(FR-SUP-01)으로 이어진다.
- 예외: 이미 가입된 이메일이면 "이미 가입된 이메일입니다"를 표시한다.
- 수용 기준
  - [ ] 주최자·공급자 가입이 각각 된다
  - [ ] 가입 화면에서 관리자 역할을 고를 수 없고, 요청을 조작해 관리자로 가입해도 거부된다

#### FR-AUTH-02 로그인·로그아웃 · 필수
- 이메일·비밀번호로 로그인한다. 로그인 후 역할별 첫 화면으로 이동한다.
  - 주최자: 내 공연 목록 / 공급자: 공고 목록(승인 전에는 심사 상태 화면) / 관리자: 심사 대기 목록
- 로그인 5회 연속 실패 시 10분간 로그인 제한 (제안).
- 수용 기준
  - [ ] 역할별로 다른 첫 화면이 열린다
  - [ ] 로그아웃 후 뒤로 가기로 이전 화면의 개인 정보가 보이지 않는다

#### FR-AUTH-03 역할 기반 접근 제한 · 필수
- 모든 기능은 2.3 권한표를 따른다. **화면에서 버튼을 숨기는 것뿐 아니라 서버에서도 검사한다.**
- 권한이 없는 요청은 거부하고, 다른 사용자의 데이터가 있는지조차 알 수 없게 응답한다 (제안: 403 대신 404).
- 수용 기준
  - [ ] 주소창에 다른 주최자의 공연 ID를 넣으면 볼 수 없다
  - [ ] 공급자가 다른 공급자의 견적 ID로 조회하면 거부된다
  - [ ] 심사 중인 공급자가 견적 제출 요청을 직접 보내도 거부된다

#### FR-AUTH-04 시연 계정 전환 · 권장
- 발표 시연을 위해 시연용 계정(주최자, 공급자 A~G, 관리자)으로 빠르게 로그인하는 기능을 **테스트 환경에서만** 제공한다.
- 운영 환경 설정에서는 이 기능이 보이지도 동작하지도 않는다.
- 수용 기준
  - [ ] 테스트 환경에서 계정 전환 한 번에 해당 역할 첫 화면이 열린다
  - [ ] 운영 설정으로 실행하면 전환 기능이 없다

### 3.2 공급자 입점·심사 (SUP) — 2번

#### FR-SUP-01 입점 신청 · 필수
- 공급자는 업체 정보와 **제공 서비스(복수 선택)** 를 입력해 입점을 신청한다.
  - 업체명, 대표 연락처, 활동 지역(시·도 복수), 제공 서비스, 소개
  - 사업자 정보는 가상 데이터로 입력한다. 실제 사업자번호 검증은 하지 않는다.
- 신청하면 상태가 `심사 중`이 된다.
- 수용 기준
  - [ ] 공간 + 음향 장비처럼 여러 부문을 한 번에 신청할 수 있다
  - [ ] 신청 후 심사 상태 화면이 보이고, 공고 목록 메뉴는 보이지 않는다

#### FR-SUP-02 관리자 심사 · 필수
- 관리자는 신청 목록에서 **승인 / 반려 / 정지**를 처리한다. 반려·정지는 사유가 필수다.
- 공급자 상태: `심사 중` → `승인` / `반려` → (재신청 시) `심사 중`, `승인` → `정지` → `승인`
- 정지된 공급자는 새 견적을 낼 수 없고, 이미 낸 견적은 주최자 화면에 "정지된 공급자" 표시와 함께 선택할 수 없게 된다 (제안).
- 모든 상태 변경은 처리자·일시·사유와 함께 이력에 남는다 (NFR-HIST-01).
- 수용 기준
  - [ ] 승인되면 공급자가 공고 목록을 볼 수 있다
  - [ ] 반려 사유가 공급자 화면에 보이고, 수정 후 재신청할 수 있다
  - [ ] 정지된 공급자의 견적 제출이 거부된다

#### FR-SUP-03 제공 서비스 관리 · 필수
- 승인된 공급자는 부문별 상세 정보를 등록·수정한다.
  - 음향 장비: 보유 장비 품목·수량 [자문: 표준 품목 목록]
  - 설치·철수: 기본 소요 시간 (분)
  - 현장 운영: 투입 가능 인원, 기본 근무 단위
- 공간 정보는 FR-SPACE-01에서 등록한다.
- 공급자는 **본인 정보만** 수정할 수 있다.
- 수용 기준
  - [ ] 다른 공급자의 정보 수정 요청은 거부된다

### 3.3 공간 (SPACE) — 등록 2번 / 탐색·선택 1번

#### FR-SPACE-01 공간 등록 · 필수
- `공간` 부문이 승인된 공급자가 공간을 등록한다. 한 공급자가 여러 공간을 가질 수 있다.
- 입력 항목
  - 이름, 지역(시·도, 시·군·구), 주소(가상), 공간 유형(전문 공연장 / 복합문화공간 / 루프탑 / 정원 / 창고 / 기타)
  - **허용 인원** (1~500)
  - **입실 가능 시각, 퇴실 마감 시각** (요일별 또는 기본값) (제안)
  - 대관료 기준 금액
  - **기본 제공 장비** (품목·수량), **기본 제공 인력** (예: 상주 엔지니어 유무)
  - **공연 허용 조건**: 밴드 공연 허용 여부, 외부 음향 장비 반입 허용, 외부 엔지니어 허용, 소음 제한 시각, 야외 여부 [자문: 필수 확인 항목]
  - 사진 (선택)
- 공연 허용 조건 중 비워 둔 항목은 `미확인`으로 저장한다.
- 수용 기준
  - [ ] 허용 인원 501 이상은 저장되지 않는다
  - [ ] 퇴실 마감이 입실 시각보다 빠르면 저장되지 않는다 (자정 넘김은 [미정])

#### FR-SPACE-02 공간 정보 수정과 과거 조건 보존 · 필수
- 공간 운영자가 원본 정보를 수정해도, **이미 공연 요청에 적용된 조건은 바뀌지 않는다.**
- 공연 요청에 공간을 선택하는 순간 그 시점의 공간 조건을 요청서에 복사해 보관한다 (스냅샷).
- 원본이 바뀌면 진행 중인 요청서에 "공간 정보가 변경되었습니다" 안내를 띄우고, 주최자가 새 정보로 다시 적용할지 고른다 (제안).
- 수용 기준
  - [ ] 공간의 기본 마이크 수를 2 → 1로 바꿔도, 이전에 선택한 요청서에는 2로 남아 있다
  - [ ] 섭외 확정된 공연의 공간 조건은 어떤 경우에도 바뀌지 않는다

#### FR-SPACE-03 공간 탐색 · 필수
- 누구나 공간 목록을 볼 수 있다.
- 필터: 지역(시·도 → 시·군·구), 공연 날짜, 예상 인원(허용 인원 이상만), 공간 유형, 밴드 공연 허용 여부
- 정렬: 대관료 낮은 순, 허용 인원 순
- 목록 카드: 이름, 지역, 유형, 허용 인원, 대관료, 기본 제공 장비 요약, 미확인 조건 개수
- 날짜 필터는 **예약 가능 여부를 보장하지 않는다.** "공간 측 확인 전"임을 표시한다.
- 수용 기준
  - [ ] 광주 / 80명 / 밴드 허용으로 필터하면 시연용 A·B·C 공간이 나온다
  - [ ] 예상 인원보다 허용 인원이 적은 공간은 나오지 않는다

#### FR-SPACE-04 공간 상세 · 필수
- 등록 정보 전체와 함께 **기본 제공 / 미확인 조건**을 구분해서 보여준다.
- 로그인한 주최자에게는 "이 공간으로 공연 요청하기" 버튼을 보여준다.
- 수용 기준
  - [ ] 미확인 조건이 "확인 필요"로 눈에 띄게 표시된다

### 3.4 공연 요청·공고 (REQ) — 1번

#### FR-REQ-01 공연 요청서 작성 · 필수
- 주최자가 공연 요청서를 작성한다. 처음 상태는 `작성 중`이다.
- 입력 항목
  - 공연명, 공연 형태(밴드 / 연극·뮤지컬 / 강연·행사 / 종교 행사 / 기타), 편성(예: 보컬 1, 기타 2, 베이스 1, 드럼 1)
  - **공연 날짜, 공연 시작·종료 시각, 리허설 시작 시각**
  - **예상 관객 수 (1~500)**
  - 지역 (공간 미정일 때 견적 범위 판단용)
  - **필요 장비** (품목·수량, 예: 보컬 마이크 4) — 모르면 비워 두고 "업체 제안 받기"를 선택할 수 있다
  - 이미 확보한 자원 (예: 자체 드럼 세트 보유)
  - 예산 (선택)
  - 요청 사항 (자유 입력)
- 필수 항목: 공연명, 공연 형태, 날짜, 공연 시각, 예상 관객, 지역
- 규칙
  - 리허설 시작 < 공연 시작 < 공연 종료
  - 공연 날짜는 오늘 이후 (제안: 최소 3일 후)
- 수용 기준
  - [ ] 예상 관객 0, 501, 문자 입력은 저장되지 않는다
  - [ ] 리허설이 공연 시작보다 늦으면 저장되지 않는다
  - [ ] 필요 장비를 비우고 "업체 제안 받기"를 선택해도 저장된다
  - [ ] 대표 시연 요청 "토요일 19~21시, 80명, 리허설 17시, 보컬 마이크 4개"를 그대로 입력할 수 있다

#### FR-REQ-02 공간 후보 선택 · 필수
- 주최자는 요청서에 공간을 붙이는 방법 중 하나를 고른다.
  - **(가) 플랫폼 공간 선택**: 공간 후보를 1개 이상 선택한다 (제안: 최대 3개). 공간 운영자는 공고에서 견적을 낸다.
  - **(나) 이미 확보한 공간 입력**: 외부에서 예약한 공간의 이름, 주소, 입실·퇴실 시각, 기본 장비, 허용 조건을 직접 입력한다. 이 경우 공간 견적은 받지 않고 장비·인력 견적만 받는다.
  - **(다) 공간 미정**: 공간 운영자와 음향업체 모두에게서 견적을 받는다 (권장)
- 선택한 공간의 조건은 요청서에 스냅샷으로 보관한다 (FR-SPACE-02).
- **공간 후보 선택은 예약 확정이 아니다.** 화면에 그렇게 안내한다.
- 선택된 공간의 허용 인원이 예상 관객보다 적으면 선택할 수 없다.
- 상태: `작성 중` → `공간 후보 선택`
- 수용 기준
  - [ ] 공간 B, C를 후보로 고르면 두 공간 조건이 요청서에 저장된다
  - [ ] 직접 입력한 공간으로 요청하면 공고에 "공간 확보됨 — 장비·인력만 요청"으로 표시된다
  - [ ] 허용 인원 50명 공간은 80명 요청서에서 선택할 수 없다

#### FR-REQ-03 공고 게시·마감 · 필수
- 주최자가 요청서를 공고로 게시한다. 상태: `공간 후보 선택` → `견적 모집`
- 공고에는 견적 마감일을 둔다 (제안: 기본 7일, 공연일 2일 전을 넘을 수 없음).
- 공고 노출 범위 [미정 — 이슈 #4]: 모든 승인 공급자 / 지역·서비스 종류 필터
- 공고에 주최자의 연락처 등 개인정보는 노출하지 않는다.
- 주최자는 마감 전에 공고를 직접 마감할 수 있다. 마감되면 새 견적을 받지 않는다.
- 수용 기준
  - [ ] 게시 후 승인된 공급자의 공고 목록에 나타난다
  - [ ] 심사 중인 공급자에게는 보이지 않는다
  - [ ] 마감된 공고에는 견적을 제출할 수 없다

#### FR-REQ-04 요청서 수정과 버전 · 필수
- 공고 게시 후 요청서를 수정하면 **새 버전**이 생긴다. 이전 버전은 지우지 않는다.
- 이미 견적을 낸 공급자에게 "요청 조건이 변경되었습니다 (v1 → v2)" 표시를 하고, 바뀐 항목을 보여준다.
- 견적은 어느 요청서 버전을 기준으로 작성됐는지 기록한다. 이전 버전 기준 견적은 비교 화면에서 "이전 조건 기준" 경고를 띄운다 (FR-CMP-01).
- `업체 확인 중` 이후에 요청서를 수정하면, 진행 중인 업체 확인은 모두 `무효`가 되고 조합 선택부터 다시 한다 (6장 수정 견적과 재합의).
- `섭외 확정` 후에는 수정할 수 없다.
- 수용 기준
  - [ ] 리허설을 17시 → 16시로 바꾸면 v2가 생기고 v1이 남아 있다
  - [ ] 견적을 낸 공급자 화면에 변경 표시가 나타난다
  - [ ] 섭외 확정된 요청서는 수정 버튼이 없고, 수정 요청도 거부된다

#### FR-REQ-05 내 공연 목록·현황 · 필수
- 주최자는 자기 공연 목록과 각 공연의 상태, 받은 견적 수, 다음에 할 일을 본다.
  - 예: "견적 3건 도착 — 비교하기", "D 사운드 수락 대기 중", "결제 대기"
- 수용 기준
  - [ ] 상태별로 다음 할 일 버튼이 다르게 보인다

### 3.5 견적 (QUOTE) — 2번

#### FR-QUOTE-01 공고 목록·상세 (공급자) · 필수
- 승인된 공급자는 공고 목록을 본다. 정렬: 마감 임박 순, 공연일 순.
- 공고 상세: 공연 조건, 필요 장비, 이미 확보한 자원, **선택된 공간 후보의 조건 스냅샷**(기본 장비, 입실·퇴실, 허용 조건)
- 공급자는 본인이 이미 견적을 낸 공고에 "제출함" 표시를 본다.
- 수용 기준
  - [ ] 공고 상세에서 공간 B·C의 입실 시각과 기본 마이크 수를 볼 수 있다
  - [ ] 다른 공급자가 낸 견적 금액·내용은 어디에서도 보이지 않는다

#### FR-QUOTE-02 견적 작성 · 필수
- 공급자는 공고에 견적을 제출한다. 한 공고에 공급자당 **유효한 견적은 1개** (수정은 버전으로).
- 견적 유형: `공간만` / `음향(장비·설치·운영 조합)` / `엔지니어 단독` / `전체 패키지(공간+음향+인력)`
  - 공급자는 승인된 부문의 유형만 고를 수 있다.
- 공간 견적은 공고에서 후보로 선택된 공간 중 하나를 대상으로 한다.
- 입력 항목
  - **품목**: 이름, 분류(마이크 / 스피커 / 믹서 / 악기 앰프 / 기타), 수량, 단가, 금액
  - **인력**: 역할(엔지니어 / 설치 인력), 인원, 근무 시작·종료 시각
  - **일정**: 대상 공간(음향 견적일 때), 설치 시작 시각, **설치 소요 시간(분)**, 철수 소요 시간(분), 입실 가능 시각(공간 견적일 때)
  - **금액**: 품목 합계, 운반비, 설치비, 인건비, 기타. **고객에게 청구되는 최종 합계(부가세 포함)** (제안) 와 **별도 비용**(포함되지 않는 항목, 예: 주차비)
  - **포함 여부 체크**: 엔지니어 포함 / 설치·철수 포함 / 운반 포함
  - 견적 유효기한 (제안: 기본 7일)
  - 기술 확인이 필요한 항목 메모 (FR-TECH-01로 연결)
- 규칙
  - 최종 합계 = 각 금액 항목의 합. 서버에서 다시 계산해 입력값과 다르면 거부한다.
  - 금액은 원 단위 정수, 0 이상.
  - 음향 견적은 대상 공간을 하나 지정해야 한다. 공간마다 다른 견적이면 공간별로 따로 제출한다 (제안) [미정]
- 수용 기준
  - [ ] D 사운드가 "추가 마이크 2개, 밴드 음향 구성, 설치·철수, 현장 기사 포함, 125만 원, 설치 90분" 견적을 낼 수 있다
  - [ ] A 라이브홀이 전체 패키지 400만 원을 낼 수 있다
  - [ ] 음향 부문만 승인된 공급자는 공간 견적 유형을 고를 수 없다
  - [ ] 합계를 조작한 요청은 거부된다

#### FR-QUOTE-03 견적 수정·철회 · 필수
- 수정하면 **새 버전**이 생기고 이전 버전은 남는다. 주최자 화면에 "수정됨 (v1 → v2)"과 바뀐 항목을 보여준다.
- 철회하면 비교 대상에서 빠진다. 철회된 견적이 포함된 조합은 `무효`가 된다.
- 조합에 포함되어 업체 확인이 진행 중인 견적을 수정하면, 그 조합의 업체 확인은 모두 `무효`가 된다.
- `섭외 확정`된 견적은 수정·철회할 수 없다.
- 수용 기준
  - [ ] D가 "설치 인력 추가, 15:45 완료, +10만 원" 수정 견적을 내면 v2(135만 원)가 생기고 v1(125만 원)이 남아 있다
  - [ ] 확정된 견적의 수정 요청은 거부된다

#### FR-QUOTE-04 받은 견적 목록 (주최자) · 필수
- 주최자는 자기 공연에 온 견적을 유형별로 본다: 전체 패키지 / 공간 / 음향 / 엔지니어
- 각 견적: 공급자명(가상 표시), 금액, 유효기한, 기준 요청서 버전, 상태(유효 / 수정됨 / 철회 / 만료)
- 유효기한이 지난 견적은 `만료`로 표시하고 조합에 새로 넣을 수 없다.
- 수용 기준
  - [ ] 다른 주최자의 공연에 온 견적은 보이지 않는다
  - [ ] 만료된 견적은 조합 선택에서 비활성화된다

### 3.6 비교·자동 검사 (CMP) — 3번

#### FR-CMP-01 조합 구성 · 필수
- 주최자는 받은 견적으로 비교할 조합을 만든다.
  - 전체 패키지 1개
  - 공간 견적 1개 + 음향 견적 1개 (+ 필요하면 엔지니어 견적 1개)
  - 직접 확보한 공간 + 음향 견적 1개
- 한 조합에 같은 유형의 견적을 2개 넣을 수 없다 (공간 2개 등).
- 음향 견적의 대상 공간과 조합의 공간이 다르면 "다른 공간 기준 견적" 경고를 띄운다.
- 조합은 여러 개 만들어 나란히 비교할 수 있다 (제안: 최대 5개).
- 수용 기준
  - [ ] A 패키지, B+D, C+D 세 조합을 만들 수 있다
  - [ ] 공간 견적 2개를 한 조합에 넣으면 막힌다

#### FR-CMP-02 자동 검사 · 필수
조합마다 아래 항목을 검사하고 결과를 `통과` / `확인 필요` / `충돌` / `경고`로 표시한다.
요청서나 견적이 바뀌면 **다시 검사한다.**

| ID | 검사 | 규칙 | 결과 |
|---|---|---|---|
| CHK-01 | 인원 | 예상 관객 ≤ 공간 허용 인원 | 넘으면 `충돌` |
| CHK-02 | 장비 수량 | (공간 기본 제공 + 견적 추가 제공) ≥ 요청 필수 수량, **품목별** | 부족하면 `충돌` (부족 수량 표시) |
| CHK-03 | 입실 → 설치 | 공간 입실 가능 시각 ≤ 설치 시작 시각 | 아니면 `충돌` |
| CHK-04 | 설치 → 리허설 | 설치 시작 + 설치 소요 시간 ≤ 리허설 시작 | 아니면 `충돌` (늦는 시간 표시) |
| CHK-05 | 엔지니어 근무 | 엔지니어 근무 시간이 리허설 시작 ~ 공연 종료를 포함 | 아니면 `충돌` |
| CHK-06 | 철수 → 퇴실 | 공연 종료 + 철수 소요 시간 ≤ 퇴실 마감 | 아니면 `충돌` |
| CHK-07 | 중복 | 이미 포함된 엔지니어·장비를 다른 견적으로 또 추가 | `경고` (예: D에 기사 포함인데 F 추가) |
| CHK-08 | 예산 | 조합 총액 > 요청서 예산 | `경고` (충돌과 구분) |
| CHK-09 | 정보 누락 | 위 검사에 필요한 값(입실 시각, 설치 시간 등)이 없음 | `확인 필요` |
| CHK-10 | 버전 | 견적이 이전 요청서 버전 기준 | `경고` "이전 조건 기준 견적" |
| CHK-11 | 유효성 | 철회·만료·정지된 공급자의 견적 포함 | `충돌` |

- 장비 수량 검사는 마이크처럼 **단순 품목부터** 한다. 품목 이름이 다르면 같은 분류로 묶어 비교한다 (제안) [자문: 품목 분류 기준]
- 소리 크기, 장비 호환성, 현장 안전은 **자동으로 판정하지 않는다.** 기술 확인(TECH) 대상이다.
- 수용 기준 (대표 시나리오)
  - [ ] **B(17시 입실) + D(설치 90분)**: 설치 완료 18:30 > 리허설 17:00 → CHK-04 `충돌`, "90분 늦음" 표시
  - [ ] **C(15시 입실) + D**: 설치 완료 16:30 ≤ 리허설 17:00 → CHK-04 `통과`
  - [ ] 요청 마이크 4개, 공간 기본 2개 + D 추가 2개 → CHK-02 `통과` / D 추가 1개였다면 `충돌` "1개 부족"
  - [ ] D(기사 포함) + F 엔지니어를 같은 조합에 넣으면 CHK-07 `경고`
  - [ ] 리허설을 16시로 바꾸면 C+D 조합이 자동으로 다시 검사되어 `충돌`이 된다
  - [ ] D 수정 견적(15:45 완료)으로 바꾸면 다시 `통과`된다

#### FR-CMP-03 비교 화면 · 필수 (대표 화면)
- 조합을 나란히 놓고 아래 항목을 같은 기준으로 보여준다.
  - 공연 조건 요약 (요청서 버전 표시)
  - 기본 제공 항목 / 추가 제공 항목
  - 포함 비용 / 별도 비용
  - **총액** (조합 내 견적 최종 합계의 합)
  - **준비 일정 타임라인**: 입실 → 설치 → 리허설 → 공연 → 철수 → 퇴실, 충돌 구간 강조
  - 자동 검사 결과 (CHK별)
  - **기술 확인 상태** (FR-TECH)
- 가격과 조건 확인 상태는 **따로** 표시한다. 싸다고 가능한 것이 아님을 보여준다.
- 업체 확인 전에는 어떤 조합도 "공연 가능 확정"으로 안내하지 않는다.
- 수용 기준
  - [ ] A 400만 / B+D 165만 / C+D 175만 세 조합이 한 화면에 보인다
  - [ ] B+D는 가장 싸지만 `충돌`로, C+D는 `통과` + 기술 확인 상태로 구분된다
  - [ ] 모바일 화면에서도 조합을 넘겨 가며 같은 항목을 비교할 수 있다

#### FR-CMP-04 조합 선택 · 필수
- 주최자는 조합 하나를 선택한다. 상태: `견적 모집` → `조합 선택`
- `충돌`이 있는 조합은 선택할 수 없다. `확인 필요`는 선택할 수 있지만 업체 확인 요청(FR-CONF-01)은 막힌다.
- 선택 시점의 요청서 버전, 견적 버전, 금액, 품목, 일정을 **스냅샷으로 저장**한다.
- 수용 기준
  - [ ] B+D 조합은 선택 버튼이 비활성화되고 이유가 보인다
  - [ ] C+D 선택 후 D가 견적을 수정해도 선택 당시 175만 원 기록이 남아 있다

### 3.7 기술 확인 (TECH) — 3번

#### FR-TECH-01 기술 확인 항목 · 필수
- 선택된 조합(또는 비교 중인 조합)에 대해, 공간 측과 음향업체가 확인할 항목을 만든다.
- 기본 항목 [자문: 최종 목록]
  - 공연(밴드) 허용 / 외부 장비 반입 허용 / 외부 엔지니어 허용
  - 전원 (용량·위치) / 반입 동선 (엘리베이터·계단·차량 진입)
  - 설치 공간 / 연결 방식 (공간 기본 장비와 외부 장비 연결)
  - 소음 제한 / 야외 운영 조건 (우천 시 등)
- 공간의 `미확인` 조건과 견적의 "기술 확인 필요 메모"가 자동으로 항목에 추가된다.
- 수용 기준
  - [ ] 공간 C의 미확인 조건이 C+D 조합의 기술 확인 항목에 나타난다

#### FR-TECH-02 기술 확인 답변 · 필수
- 각 항목의 담당자(공간 측 / 음향업체)가 `확인됨` / `조건부` / `불가`와 메모를 남긴다.
- 기록에는 **담당자, 확인 일시, 대상 요청서 버전, 대상 견적 버전**을 함께 저장한다.
- 요청서나 대상 견적이 새 버전이 되면 기존 답변은 `재확인 필요`로 바뀐다.
- `불가` 답변이 하나라도 있으면 그 조합은 `충돌`로 표시된다.
- 수용 기준
  - [ ] C 컬처스페이스와 D 사운드가 각자 담당 항목에 답변할 수 있다
  - [ ] 남의 담당 항목에는 답변할 수 없다
  - [ ] 리허설 변경(v2) 후 이전 답변이 `재확인 필요`로 바뀐다
  - [ ] E 오디오 견적이 포함된 조합은 미확인 항목이 남아 `확인 필요`로 보인다 (시연용)

### 3.8 업체 최종 수락 (CONF) — 4번

#### FR-CONF-01 업체 확인 요청 · 필수
- 주최자가 선택한 조합으로 업체 확인을 요청한다. 상태: `조합 선택` → `업체 확인 중`
- 요청 조건
  - 자동 검사에 `충돌`, `확인 필요`가 없다
  - 필수 기술 확인 항목이 모두 `확인됨` 또는 `조건부`다
- 조합에 포함된 **공급자마다** 확인 요청이 하나씩 생긴다. 확인 상태: `대기`
- 확인 기한을 둔다 (제안: 요청 후 48시간, 견적 유효기한을 넘을 수 없음).
- 수용 기준
  - [ ] 기술 확인이 남은 조합은 확인 요청 버튼이 비활성화되고 남은 항목이 보인다
  - [ ] C+D 조합으로 요청하면 C와 D에게 각각 확인 요청이 간다

#### FR-CONF-02 수락·거절 · 필수
- 각 공급자는 **자기 담당 범위, 금액, 최종 일정**을 확인하고 `수락` / `거절`(사유 필수)한다.
- 업체 확인 상태: `대기` → `수락` / `거절` / `만료`(기한 경과) / `무효`(조합 변경)
- 한 공급자라도 거절하면 조합은 결제 불가가 되고, 주최자에게 다른 조합을 고르도록 안내한다. 상태는 `조합 선택`으로 돌아간다.
- 기한이 지나면 `만료`되고, 주최자는 일정 재확인을 다시 요청할 수 있다 (새 확인 요청).
- **새 조합이나 수정된 조건에는 새 확인 기록을 쓴다.** 이전 수락을 재사용하지 않는다.
- 모든 공급자가 수락하면 상태: `업체 확인 중` → `결제 대기`
- 수용 기준
  - [ ] C와 D가 모두 수락하면 결제 대기가 된다
  - [ ] D가 거절하면 결제 버튼이 나타나지 않고 재선택 안내가 보인다
  - [ ] 175만 원 조건에 대한 수락은 185만 원으로 바뀐 조건에 사용되지 않는다
  - [ ] 기한이 지난 확인 요청은 `만료`로 바뀐다

#### FR-CONF-03 확인 현황 (주최자) · 필수
- 주최자는 업체별 확인 상태, 남은 기한, 거절 사유를 한 화면에서 본다.
- 수용 기준
  - [ ] 업체별 상태와 남은 시간이 표시된다

### 3.9 테스트 결제·확정 (PAY) — 4번

#### FR-PAY-01 테스트 결제 · 필수
- `결제 대기` 상태에서만 결제할 수 있다. 결제 화면에 **"테스트 결제 — 실제 청구되지 않습니다"** 를 표시한다.
- 결제 금액은 **서버가 조합 스냅샷으로 계산한 총액**이다. 화면에서 보낸 금액은 믿지 않는다.
- 결제 수단: 결제 대행사 테스트 모드 또는 모의 결제 [미정 — 설계 단계]
- 결제 직전에 다시 검사한다: 모든 업체 `수락`, 기한 내, 견적·요청서 버전이 수락 당시와 동일.
- 수용 기준
  - [ ] 업체 하나라도 수락하지 않은 조합은 결제 화면에 들어갈 수 없고, 결제 요청을 직접 보내도 거부된다
  - [ ] 금액을 조작한 결제 요청은 거부된다

#### FR-PAY-02 결제 결과 처리 · 필수
- **결제 성공은 서버에서 확인한 뒤에만** 섭외 확정한다. 화면의 "성공" 이동만으로 확정하지 않는다.
- 결제 시도 상태: `진행 중` → `성공` / `실패` / `취소`
- 실패·취소는 확정하지 않고 `결제 대기`로 돌아간다.
- **같은 결제 응답이 여러 번 와도 한 번만 반영한다** (멱등 처리).
- **한 공연에서 두 조합이 동시에 확정되지 않는다.**
- 성공하면 상태: `결제 대기` → `섭외 확정`
- 수용 기준
  - [ ] 결제 실패 시 섭외 확정되지 않는다
  - [ ] 같은 성공 응답을 두 번 보내도 주문·결제 기록이 하나다
  - [ ] 결제 버튼을 두 번 빠르게 눌러도 결제가 한 번만 진행된다

#### FR-PAY-03 섭외 확정·최종 담당표 · 필수
- 섭외 확정되면 주최자와 조합의 공급자들이 **최종 담당표**를 본다.
  - 업체별 담당 범위, 품목, 인원, 금액
  - 최종 일정: 입실 → 설치 → 리허설 → 공연 → 철수 → 퇴실
  - 업체별 정산 예정액 (테스트 표시, 실제 정산 없음)
  - 기술 확인 기록 요약
- 확정 후 요청서·견적·조합은 변경할 수 없다. 결제 후 변경·추가 결제·환불은 후속 범위다.
- 수용 기준
  - [ ] C+D 확정 후 주최자, C, D가 같은 담당표를 본다
  - [ ] 조합에 없는 공급자(B, E 등)는 담당표를 볼 수 없다

### 3.10 관리자 (ADMIN) — 2번 + 4번

#### FR-ADMIN-01 관리자 메뉴 · 필수
- 한 메뉴에서 공급자 심사(FR-SUP-02)와 거래 이력(FR-ADMIN-02)을 오간다.

#### FR-ADMIN-02 거래 이력 조회 · 필수
- 공연별 상태 변경 이력, 업체 확인 기록, 결제 시도 기록을 조회한다.
- 관리자는 조회만 할 수 있고, 수락·결제를 대신 처리하지 않는다.
- 수용 기준
  - [ ] C+D 시나리오의 상태 변경이 시간순으로 모두 보인다

#### FR-ADMIN-03 게시 정보 관리 · 권장
- 부적절한 공간·공급자 정보를 숨김 처리한다 (사유 필수).

### 3.11 시연 데이터 (DEMO) — 공통

#### FR-DEMO-01 초기 데이터 · 필수
- 총계획서 5장의 가상 공급자 7곳(A~G), 공간(A·B·C), 시연용 주최자·관리자 계정을 시드 데이터로 넣는다.
- 모든 이름은 가상이며 화면에 "가상 업체" 표시를 한다. 실제 업체명·개인정보를 쓰지 않는다.
- 시드 데이터는 결과가 미리 정해진 화면이 아니라, **실제 서버·DB를 통해** 견적 수정·수락·결제가 동작해야 한다.
- 수용 기준
  - [ ] 시드 적용 후 대표 시나리오 B를 처음부터 끝까지 진행할 수 있다
  - [ ] 진행 결과가 새로고침 후에도 유지된다

#### FR-DEMO-02 시연 데이터 초기화 · 필수
- 관리자가 테스트 환경에서만 데이터를 초기 상태로 되돌린다. 일반 사용자 기능과 분리한다.
- 수용 기준
  - [ ] 운영 설정에서는 초기화 기능이 동작하지 않는다

### 5.2 상태 흐름

**공연 진행**
```
작성 중 → 공간 후보 선택 → 견적 모집 → 조합 선택 → 업체 확인 중 → 결제 대기 → 섭외 확정
                                       ↑              │              │
                                       └── 거절·만료·조건 변경 ───────┘
```
- 결제 실패·취소: `결제 대기` 유지
- 공연 취소 (주최자): `섭외 확정` 전 어느 단계에서나 `취소` (제안)

**공급자**: `심사 중` → `승인` / `반려`, `승인` ↔ `정지`
**견적**: `유효` → `수정됨`(새 버전) / `철회` / `만료`
**업체 확인**: `대기` → `수락` / `거절` / `만료` / `무효`
**기술 확인 항목**: `미확인` → `확인됨` / `조건부` / `불가` → (조건 변경 시) `재확인 필요`
**결제 시도**: `진행 중` → `성공` / `실패` / `취소`

공간 후보 선택, 기술 확인, 업체 수락, 결제 완료는 **서로 다른 상태**로 관리한다.
